# Spring-Boot-React-CRM 章程

## 核心原则

### 一、契约优先的 API 设计（不可协商）

OpenAPI 规范是 Spring Boot 后端与 React 前端之间每个 REST 端点的唯一事实来源。

- 任何端点在契约被定义、评审并版本化之前，不得实现或调用。
- 后端 DTO 与前端 API 客户端类型必须由同一份契约生成。
- 破坏性变更必须引入新的 API 版本并提供弃用路径；契约不得被静默修改。
- 每次契约变更都必须附带一个测试，验证文档化的请求/响应结构。

### 二、分层架构与关注点分离

后端遵循 Controller → Service → Repository 分层；前端组件保持表现层纯净。

- 业务逻辑必须只存在于 Service 层；Controller 只处理 HTTP 关注点，Repository 只负责持久化。
- 前端组件不得包含业务规则；数据访问必须通过专用的 API 客户端层。
- 任何业务规则不得内嵌于 SQL、JSX 或 UI 事件处理器中。

### 三、数据完整性、安全与校验（不可协商）

每个信任边界都必须校验输入，所有变更请求都必须经过认证与授权。

- 所有 DTO 必须声明 Jakarta Bean Validation 约束；后端是强制执行点，前端校验仅用于改善用户体验。
- 授权必须在服务端强制执行（Spring Security、JWT/OAuth2）；仅隐藏 UI 元素绝不构成访问控制。
- 密码必须使用 bcrypt/Argon2 哈希存储，密钥必须通过环境配置或密钥管理服务管理——绝不写入日志或提交到代码库。
- 事务必须显式声明并限定在 Service 层；禁止绕过 Service 层的临时批量写入。

### 四、测试优先与质量门禁（不可协商）

测试先于实现编写（红 → 绿 → 重构），并作为每次合并的关卡。

- 后端：JUnit 5 + Spring Boot Test；前端：Jest + React Testing Library。
- 每次合并必须通过构建、单元测试、集成测试、Lint、类型检查以及已配置的覆盖率门槛。
- 必须遵循测试金字塔：大量单元测试、少量集成测试、极少量端到端测试。

### 五、简洁、可维护与可观测

从满足当前需求的最简设计开始。

- YAGNI：禁止投机性抽象或无用依赖；每个库都必须证明自身存在的价值。
- 必须使用结构化日志（SLF4J）；每个用户可见的错误都必须在服务端记录。
- 列表端点必须分页；禁止 N+1 查询模式。
- 代码首先为人类读者而写；命名与结构应传达意图。

## 技术与架构约束

- 后端：Java（LTS）+ Spring Boot，使用 Maven 或 Gradle；仅使用 REST + JSON；业务功能不得使用服务端页面渲染。
- 前端：React + TypeScript；只采用一种状态管理方案；API 客户端由 OpenAPI 契约生成。
- 数据：关系型数据库 + 版本化 schema 迁移（Flyway/Liquibase）；schema 变更必须附带迁移计划。
- 安全：Spring Security；JWT/OAuth2 认证；基于角色的授权与 CRM 领域角色对齐（如 admin、销售、客服）。
- 配置：按环境使用 profile；密钥绝不硬编码。

## 开发工作流与质量门禁

- 功能遵循 Spec Kit 流程：/speckit-specify → /speckit-plan → /speckit-tasks → /speckit-implement → /speckit-converge。
- 每个拉取请求必须通过 CI（构建、测试、Lint、类型检查、覆盖率）并由至少一位其他开发者评审后才能合并。
- 提交信息必须遵循 Conventional Commits 规范。
- 未关联已跟踪 issue 的 TODO/FIXME 不得合并；schema 变更必须附带迁移计划。

## 治理

- 本章程取代本项目的一切临时约定与非正式实践。
- 修正案流程：提出变更 → 记录理由 → 评审并批准 → 升版本号 → 更新本文件。
