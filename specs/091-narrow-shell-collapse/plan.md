# 实施计划：窄屏外壳内容区塌陷修复（091）

**Branch**: `appmod/java-upgrade-20260912235322` | **Date**: 2026-09-14 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/091-narrow-shell-collapse/spec.md`

## 摘要

窄屏（<768px）下整个内容区的宽度**恒为 0**：内容**渲染完整**（实测内容宽 141–633）
却挤在一条 24px 的缝里，用户既看不见也点不到，且**没有横向滚动条**这条退路。

根因是**组件库的一条补偿规则与外壳的主轴方向冲突**：库对「含侧边栏的布局」写了
`其内部布局容器宽度为 0`，靠**行向**的可伸缩把宽度长回来；外壳在窄屏把主轴改成**纵向**，
可伸缩作用到了高度上，宽度就停在 0。**内联样式能改方向，改不了那条作用在子节点上的规则。**

做法：**窄屏不再渲染侧边栏组件**，改用普通容器承载既有的横向菜单。
一刀同时解决两处缺陷——① 布局不再被识别为「含侧边栏」，`width: 0` 的前提消失；
② 菜单条从 200×200 的方块变成 375×48 的整宽横条（两处变动的**机制**已在浏览器里先验证过，见 research.md §1/§2）。

**为什么不是一行了事的 CSS 覆写**：测试环境没有布局引擎，CSS 覆写修好之后
**测试能看到的东西与修之前完全一样**——又一次「改坏了没人知道」。
结构化改动把一条**与缺陷有确定因果、且不依赖布局引擎**的前提带进测试环境（research.md §5）。

## 设计

### 缺陷①的修法：不再让布局被识别为「含侧边栏」

组件库的判定有两条来源：**子节点里有没有侧边栏组件**，以及**有没有侧边栏通过上下文登记过自己**。
窄屏不再渲染该组件后，两条来源同时为空 —— 这在浏览器里**先验证过**：
把那个类名从运行时的 DOM 上摘掉，内容容器立刻从 **0 → 351**、内容区可见宽从 **24 → 375**（research.md §2 表）。
**351 正是 SC-001 预测的值**，不是事后凑的。

### 缺陷②的修法：菜单条换成普通容器

窄屏下用一个**不定宽、整宽、定高（48）**的普通容器承载**既有的**横向菜单（含既有的拍平逻辑）。
**机制先验证过**：把侧边栏容器改成这三个尺寸后实测 **375×48**（同上表），与代码注释声明的形态一致。

**不使用侧边栏组件传「整宽」的做法**：它内部把宽度写成 `flex: 0 0 <宽度>`，
在纵向主轴下 `100%` 会变成**高度** 100%（research.md §1 的备选表）。

### 宽屏路径：一个字符都不动

宽屏分支的 JSX 与尺寸（侧边栏 200 / 折叠 64、内容区边界、页脚）**原样保留**；
外层布局仍然只在窄屏改主轴方向。FR-W-009 要求**宽屏 DOM 与几何逐项相同**——
实现时**不得**为了「顺手统一」而重排宽屏那支。

### 判据：几何走浏览器，结构走单测

| 判据 | 形态 | 位置 |
|---|---|---|
| SC-001 / SC-002 / SC-003（宽度、菜单条几何） | **浏览器实测**（可复跑脚本） | `specs/091-narrow-shell-collapse/measure-narrow-shell.mjs` |
| SC-004（宽屏零变化） | **浏览器实测**，五档宽度逐项比对 | 同上 |
| SC-006（结构前提 + 会红） | **单元测试**（结构断言，不依赖布局引擎） | `frontend/src/App.render.test.tsx`（新增用例，与既有窄屏用例**并列不重复**） |
| SC-005（门禁四道） | 命令 | 见「验证」 |

**不新增单独的外壳组件**：把外壳抽成可单独渲染的组件会改动宽屏的渲染树，
与「宽屏零变化」直接冲突；新用例沿用该文件既有的 mock 组合渲染整壳。

## 关键决策

1. **结构化改动而非 CSS 覆写** —— 决定性理由是**可测性**（research.md §1）。
2. **不在窄屏新增 `!important`**（FR-W-008）—— 本仓正在分步退役对抗性 CSS，不重新铺开。
3. **不抽新的外壳组件** —— 抽出来会改动宽屏渲染树，与 FR-W-009 冲突。
4. **判据分层**：几何→浏览器脚本，结构→单测；**不试图在 jsdom 里断言几何**（会得到假绿灯）。
5. **不用 `matchMedia` 做判据** —— 测试环境把它桩成恒 false（research.md §3 第 2 条）。
6. **不改窄屏判据与断点值** —— 改它同时影响搜索框、通知等的显隐，回归面远超本项。
7. **不升组件库版本** —— 升版会改布局实现，使全部实测基线失效。
8. **既有窄屏用例保持原样** —— 它保护的是「菜单被拍平」这个**行为**，
   新用例保护的是**结构前提**；两者不重复，**不得**为了「凑覆盖」把既有用例改写掉。
9. **不做各页面的窄屏适配** —— 判据只锚外壳几何（spec 非目标第 1 条）。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| **宽屏被改坏**（外壳是全站共用，影响面大于原缺陷） | 宽屏分支原样不动；SC-004 五档逐项比对；FR-W-009 明文禁止改宽屏 DOM/类名 |
| **跨断点切换后类名残留**（侧边栏卸载、库内登记表理论上随之清空，但**本轮未直接量**） | research.md §7 第 1 条列为**必测项**：宽→窄→宽来回切换后，窄屏下始终不出现、宽屏下重新出现，且回宽屏几何与初始逐项相同 |
| **新用例写成「实现耦合」而非「因果断言」** | 断言目标选的是**那条 `width:0` 的命中前提**（research.md §5 论证了因果）；并在注释里写明「它为什么与缺陷有因果关系」 |
| **新用例「绿而没执行窄屏」** | 覆盖**挂载即窄屏**的路径（FR-W-010）；并用定向破坏证明它会红 |
| **顺手扩到页面级窄屏适配** | spec 非目标第 1 条；判据只锚外壳几何 |
| **菜单条内部观感未逐项量**（只截图核对过） | quickstart 的截图清单里逐页看；观感问题不等于本项失败，须另立一项 |
