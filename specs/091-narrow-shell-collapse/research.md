# 调研记录：窄屏外壳内容区塌陷修复（091）

**日期**：2026-09-14
**口径**：本文所有「实测」都在真实 Chromium 里量（Playwright 打 `http://localhost:5173`，
`admin/admin123` + 验证码 `0000`），所有「读源」都给出文件与符号。
**区分标注**：`【实测】` = 本轮在浏览器/测试运行器里量到的；`【读源】` = 读组件库或本仓源码得到的；
`【推导】` = 由前两者推得、**本轮未直接量**。

## §1 修复形态：结构化改动，不是 CSS 覆写

**Decision**：窄屏**不再渲染侧边栏组件**，改用普通容器承载既有的横向菜单。
不使用 `!important` 覆写组件库的 `width: 0`。

**Rationale（三条，按决定性排序）**：

1. **只有结构化改动能被自动化判据抓住。**
   测试环境**没有布局引擎**（§3），断言不了宽度。CSS 覆写修好之后，
   测试能看到的与修之前**完全一样**——又一个「改坏了没人知道」。
   结构化改动则把一条**与缺陷有确定因果的可断言前提**带到测试环境里（§5）。
2. **`width: 0` 作用在子节点上，内联样式够不着。**
   本仓已经踩过一次：外壳给外层布局加了内联的排列方向（§2 实测其生效），
   但那条规则的**承受者是它的子元素**，外壳既有的内联样式对它无能为力。
   继续在外层加内联样式无法治本。
3. **本仓正在分步退役对抗性 CSS**（另一编号规格的 P4 阶段），
   在窄屏新增一条 `!important` 会把那笔债重新铺开（需求 FR-W-008 已明文禁止）。

**Alternatives considered**：

| 备选 | 否决理由 |
|---|---|
| 加 `!important` 覆写 `width: auto` | 见 Rationale 1/3：不可测，且违反 FR-W-008 |
| 给外层布局传「无侧边栏」的 prop | 只修缺陷①；侧边栏仍是 200×200 方块（§2 实测），缺陷②原样留下 |
| 保留侧边栏组件、把宽度传成 `100%` | 【读源+推导】组件库把它写成 `flex: 0 0 <宽度>` 与 `width: <宽度>`（`antd/es/layout/Sider.js:149,152`）。在**纵向**主轴下 `flex-basis: 100%` 是**高度** 100%——而「主轴上的固定尺寸压掉声明高度」这一点**已被实测**（§2：传 `undefined`→200 时实测 200×200，而同时声明的 48 被压掉）。故该备选会把菜单条变成整屏高 |

## §2 窄屏外壳的可行形态：普通容器 + 既有横向菜单

**Decision**：窄屏下用一个**不定宽、整宽、定高**的普通容器承载既有的横向菜单；
菜单项沿用既有的「拍平成一级项」逻辑，**不新增抽屉/汉堡**（spec 非目标第 2 条）。

**实测依据**：在真实页面上把侧边栏容器改成「不定宽 + 整宽 + 定高」后量到的几何——

| 页面 | 改动前（缺陷态） | 缺陷①单独修好后 | 缺陷①②都修好后 |
|---|---|---|---|
| `/stats` | 内容容器 **0**，内容区可见宽 **24** | 内容容器 **351**，可见宽 **375** | 菜单容器 **375×48** |
| `/customers` | 同上 | 同上 | 同上 |
| `/orders` | 同上 | 同上 | 同上 |
| `/roles` | 同上 | 同上 | 同上 |
| `/tags` | 同上 | 同上 | 同上 |

- 五页一致：**内容容器 351**（＝375 − 内容区自身左右内边距各 12），**内容区可见宽 375**。
- 菜单容器 **375×48**，与内容区同宽（375）。
  ~~—— 与代码注释声明的「顶部横向滚动」一致。~~
  **【2026-09-14 订正】**后半句**不成立**，原文保留在上。实测 `menuScroll` 的
  `scrollWidth == clientWidth == 375`——**没有可滚动的余量**，故不存在横向滚动。
  真实形态是 antd 横向菜单的**溢出折叠**：放不下的入口收进右侧 `...` 触发器的浮层里
  （上一条「右侧有折叠指示」的肉眼观察与此吻合，是它先对了、推论先错了）。
  可达性已单独取证：0 个入口被裁成死区、点击可导航到 `/customers`。
  故 `spec.md` 非目标第 2 条与 `App.tsx` 的注释均已改为实测口径（结论不变、描述改正）。
- 五页的**页面级横向溢出均为 0**（`documentElement.scrollWidth == innerWidth`），
  即修复**不会**引入页面左右晃动（spec 边界情形）。
- 肉眼核对截图：顶部是一条整宽的菜单条（首页／线索／客户／…，右侧有折叠指示），

**`【推导】` 未直接量的部分**：菜单条内部「整宽 48px 高 + ~~横向菜单~~ **溢出折叠菜单**」的**观感**
（菜单项高度、分隔线、折叠指示的位置）本轮只做了截图核对，未逐项量；
实现后按 `quickstart.md` 的截图清单再看一遍。

## §3 测试可行性：能跑到窄屏，但断言不了几何

**Decision**：窄屏的**几何**判据走浏览器实测脚本；**结构**判据走单元测试。
**不使用** `matchMedia` 作为任何判据。

**实测的三条事实**：

1. **`window.innerWidth` 可写【实测】**。在测试运行器里探测：
   - 默认值 **1024**；
   - 直接赋值 `window.innerWidth = 375` → **生效**（读回 375）；
   - `Object.defineProperty(..., {writable:true, configurable:true})` → 生效；
   - 派发尺寸变化事件后仍为 375；按同样手法可**还原**为 1024。
   ⇒ 「窄屏分支能被单测真的走到」成立。
2. **`matchMedia` 不可信【实测+读源】**：测试环境的 `matchMedia('(max-width: 767px)').matches`
   实测为 **false**（`src/test/setup.ts` 把它桩成恒 false，因为 jsdom 未实现它）。
   ⇒ 凡是用 `matchMedia` 写的判据，在单测里**恒为宽屏**，会静默失真。
   **本仓的外壳用的是 `window.innerWidth < 768`，不是 `matchMedia`**——这是它能被测的前提。
3. **没有布局引擎【读源+既有经验】**：`clientWidth` / `getBoundingClientRect()` /
   计算后的 `gridTemplateColumns` 在测试环境里全是假值。
   ⇒ 几何判据**只能**在浏览器里成立，必须做成可复跑的脚本（与既有取证脚本同形制）。

## §4 订正：窄屏分支**不是**零执行（本轮推翻了自己的初稿）

**先说错的**：初稿声称「窄屏分支从未被自动化用例执行过」。**这是错的**，本轮已订正。

**实测**：单独跑既有用例 `App.render.test.tsx` 的 `窄屏（<768px）把分组拍平成一级项，resize 事件触发形态切换`，
**通过**；该用例把 `window.innerWidth` 设为 375 并派发尺寸变化事件，
断言「分组标题消失」「组内项升为一级项」——**这两条断言只有在窄屏分支成立时才通过**。
⇒ 窄屏分支**每次全量测试都真的执行了**。

**那么缺陷为什么活下来了**——三层，且是递进的：

1. **断言全落在文案上，而文案在缺陷下完全正常。** 用例验的是「菜单被拍平」，
   而内容区宽度塌陷**不影响任何文案**（实测内容宽 141–633，内容渲染完整）。**它测的是能测的那部分，不是坏掉的那部分。**
2. **几何在测试环境里量不出来**（§3 第 3 条）⇒ 这一层即使有人想断言也无从下手。
3. **有一条本可断言的因果链，但没有任何断言碰它**（§5）。

**另有一条真实覆盖空洞**：既有用例走的是「**先按宽屏渲染，再 resize 到窄屏**」，
而「**挂载时就已经是窄屏**」（窄屏判定的**初值**）从未被覆盖 ⇒ 需求 FR-W-010。

**这条订正的处置**：spec.md 与 `checklists/requirements.md` 均已就地改写并留痕（不静默），
并同步订正了一条把该错误结论当作通用规律记下来的长期笔记。

## §5 判据形态：断言「使布局塌陷的那个前提」

**Decision**：单元测试断言的目标是**让组件库把该布局识别为「含侧边栏的布局」的那个前提**
（外壳容器上的一个类名）在**窄屏下不成立**、在宽屏下成立。

**为什么这条断言是「因果」而不是「实现耦合」【读源】**：

- 组件库的规则是 `含侧边栏的布局 → 其内部的布局容器宽度为 0`
  （`antd/es/layout/style/index.js` 的 `hasSider` 分支），
  它同时把该布局设成**横向**（`flexDirection: 'row'`）。
- 那个类名**就是这条规则的命中前提**：类名在 ⇒ `width: 0` 生效；类名不在 ⇒ 规则不触发。
- 外壳在窄屏把主轴改成纵向，于是补偿失效、宽度停在 0（§2 实测）。
- ⇒ 「窄屏下该类名不存在」与「内容区宽度不再为 0」是**确定的因果关系**，
  不是「断言了某个恰好为真的实现细节」。**这也正是它能被证伪的原因**（把窄屏改回旧写法，该类名重新出现，用例变红）。

**同时**：该断言**不依赖布局引擎**，因此是本项里**唯一**能在测试环境里落地的、与缺陷直接相关的判据。

## §7 已知风险与未验证项（如实列出）

1. **跨断点切换后类名是否残留**：从宽屏拖到窄屏时，侧边栏组件会卸载；
   组件库内部的「已注册侧边栏」登记表**理应**随之清空，但**本轮未直接量**。
   实现后必须实测：宽屏 → 窄屏 → 宽屏 来回切换后，该类名在窄屏下**始终不出现**、
   在宽屏下**重新出现**，且回到宽屏的几何与初始**逐项相同**。
2. **菜单条内部观感**（§2）未逐项量，只做了截图核对。
3. **实现后窄屏的页面级观感**（表格挤压、表单拥堵）**预期仍然存在**，
   且按 spec 的假设**不计为本项失败**——这与「内容看不见」是两回事，验收时不要混谈。
4. **既有窄屏用例与新用例的分工**：既有用例断言**文案**（拍平），新用例断言**结构**（前提），
   两者**不重复**；不要为了「凑覆盖」把既有用例改写成结构断言（会丢掉拍平行为的保护）。
