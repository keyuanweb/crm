# 任务清单：窄屏外壳内容区塌陷修复（091）

**Input**: Design documents from `/specs/091-narrow-shell-collapse/`

**Prerequisites**: [spec.md](./spec.md)（必需）、[plan.md](./plan.md)（必需）、[research.md](./research.md)（必需，取证与订正底稿）、[quickstart.md](./quickstart.md)（验证步骤）

**Tests**: **必需**（FR-W-007 / FR-W-010）。判据**分两层**：几何走浏览器实测脚本，结构走单测。
**不试图在单测里断言几何**——测试环境没有布局引擎，量出来的是假值（research.md §3）。

**Organization**: 按「前置取证 → 前置判据（测试先行）→ 逐条用户故事 → 收尾」分组。

## 格式：`[ID] [P?] 说明`

- **[P]**：可并行（不同文件、无未完成依赖）
- 每项任务均含**确切文件路径**
- **实测证据一律内嵌日期**；口径有边界的，边界一并写明

> **编号消歧**：本文档的 `T0xx` 属于本规格，与 `specs/083-*`、`085-*`、`086-*`、`087-*`、`088-*`、`090-*` 的同名编号**无关**。

> **⚠️ 两项如实告知（不得省略）**
> 1. **两处缺陷由同一次代码改动修复**（US1 与 US2 共用 T005）。**不是**把它们拆成两次提交——
>    拆开会产生一个「窄屏下菜单整个消失」的中间提交，那不是可交付状态。
>    两条用户故事各自**独立验证**（T006/T007 与 T008/T009），但**共用一次实现**。
> 2. **本项不做各页面的窄屏适配**（表格横向滚动、表单单列、弹窗宽度）。窄屏下这些观感问题
>    **预期仍然存在**，且**不是**本项失败（spec 非目标第 1 条、quickstart §五）。

## Phase 3: US1 —— 窄屏能看见内容（P1，MVP）

**目标**：窄屏下内容区占据视口全部可用宽度。**独立判据**：内容区可见宽 = 视口宽 − 内容区自身内边距。

- [x] **T005** [US1] `frontend/src/App.tsx`：**窄屏分支不再渲染侧边栏组件**，
  改用普通容器承载**既有**的横向菜单（复用既有的菜单拍平逻辑与菜单项来源）；
  **宽屏分支原样不动**（含侧边栏 200 / 折叠 64、内容区边界、页脚）。
  **这一改同时消除两处缺陷**：① 布局不再被识别为「含侧边栏」⇒ 那条 `宽度为 0` 的规则不再命中；
  ② 菜单条从固定方块变成整宽容器。**改动前先验证过机制**（research.md §2 的实测表）。
  **不得**新增 `!important`（FR-W-008）；**不得**为了「顺手统一」重排宽屏那支（FR-W-009）。
  **`index.css` 只在需要定样式且无法内联时改动**，且**不得**新增覆盖组件库布局类名的全局规则。
- [x] **T006** [US1] 实测内容区几何（SC-001/SC-002，日期内嵌）：
  四档窄屏 × 采样四页，**内容区可见宽（`.page-scroll` 的 `clientWidth`）= 320 / 375 / 414 / 767**
  （＝视口宽）；**内容容器宽（`.page-container`）= 296 / 351 / 390 / 743**（＝视口 − 24）；
  **页面级横向溢出 = 0**。
  > **⚠️ 2026-09-14 订正**：本条原写作「内容区可见宽 = 296 / 351 / 390 / 743（＝视口 − 24）」——
  > **量错了元素**。那一组数是**内容容器**的宽；内容区可见宽实测是**视口宽本身**（375 档 375）。
  > 缺陷态同理：内容区可见宽 24（不是 0）、内容容器 0。**两个量分别量、分别报，不得互换。**
  > 原文已由 spec.md 的「订正块」完整留痕，此处不再复写。
  边界写明：窄屏下**内容区实际内容宽仍会大于可见宽**（表格横向滚动）是**预期的**，不计为失败。
- [x] **T007** [US1] 边界实测（FR-W-005）：**767 走窄屏、768 走宽屏**，两侧判据分别成立
  （767 用窄屏口径，768 用宽屏口径，两者不同，都要看）。

## Phase 4: US2 —— 窄屏菜单是一条，不是方块（P2）

**目标**：窄屏菜单是**整宽**的横向菜单条。**独立判据**：菜单容器宽 = 内容区可见宽、高 = 48。

> 本阶段的实现在 T005 里已完成（见文首「如实告知」第 1 条），本阶段是**独立的验证**。

- [x] **T008** [US2] 实测菜单条几何（SC-003，日期内嵌）：375 档菜单容器 **375×48**
  （宽 = 内容区可见宽 = 视口宽 375，**不是 351**），**不再是 200×200**；
  确认菜单项**可达**（**溢出折叠**进 `...` 展开，不是被裁剪成死区——
  实测 `scrollWidth == clientWidth == 375`，**没有可滚动余量**，故原写的「横向滚动」与实测不符，
  已订正），并留存窄屏截图。
- [x] **T009** [US2] 跨断点切换实测（research.md §7 第 1 条，**本轮未直接量过，必测**）：
  宽 → 窄 → 宽 来回切换后，① 窄屏下该前提**始终不出现**；② 拖回宽屏后它**重新出现**、侧边栏可见；
  ③ 回宽屏后的几何与**初始**逐项相同（不残留窄屏的内联样式）。

拆并行只会让「谁改了什么」不可归因。**不要**为了让任务看起来更多而拆并行。

## 实施策略

- **MVP = US1（T001~T007）**。做完这一段，窄屏从「完全不可用」变成「可用」，
  菜单条还是个方块（US2 未做）——但用户已经能读能点了。
- **US1 与 US2 共用 T005 一次改动**，故实际交付点是 T005 完成之后；两者只差验证。
- **US3（T010）不可跳过**：外壳改动的影响面是全站，宽屏被改坏比原缺陷更严重。
- **US4（T011）不可跳过**：它是「这个缺陷为什么能活到今天」的答案，
  也是本项唯一能把同类回归挡在门外的东西。
- **本项规模小是刻意的**：spec 的非目标明确划出了各页面窄屏适配。
  把它们并进来会让本项从「一处外壳修复」膨胀成「移动端改版」，判据也随之失去可证伪性。
