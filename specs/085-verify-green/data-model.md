# 数据模型：验证门禁转绿（085）

## 0. 首要声明：本规格**不改变任何数据库 schema**

**无 Flyway 迁移**（FR-V14 的范围守卫）。已核实的三条依据：

| 关注点 | 实测结论 | 依据 |
|---|---|---|
| 新增 `PENDING` 取值是否需要迁移 | **不需要** —— 该列是 `VARCHAR(20)`，**不是 ENUM**，且该表此后无任何 `ALTER` | `V63__open_platform.sql:35-49` |
| 定向更新 `last_login_at` 是否需要新列 | **不需要** —— 列已存在 | `V1__init.sql` 的 `user` 表 |
| 错误码 `CLOSE_RESULT_REQUIRED` 是否需新增 | **不需要** —— 已存在且已是 422 | `ErrorCode.java:29` |

因此本文件描述的不是"表结构"，而是**本规格触及的三个语义模型**：投递记录的状态机、乐观锁令牌的语义边界、错误码到 HTTP 状态的映射模型。

## 1. 实体：投递记录（`webhook_delivery`）

### 1.1 状态机（本规格**新增**的状态迁移）

```
                    ┌──────────────────────────────────┐
   派发 ──────────► │ PENDING（投递中）                 │   ← 本规格新增
                    └───────────────┬──────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              │ 重试循环结束（成功 / 用尽重试 / URL 被拒）  │ 进程终止（残留）
              ▼                                            ▼
    ┌──────────────────┐ ┌──────────────────┐   ┌──────────────────┐
    │ SUCCESS          │ │ FAILED           │   │ FAILED           │
    │                  │ │                  │   │ reason=中断残留   │
    └──────────────────┘ └──────────────────┘   └──────────────────┘
                                                       ▲
                                              启动清扫（FR-V07）
```

### 1.2 状态取值与语义

| 取值 | 语义 | 是否**终态** | 由谁写入 |
|---|---|---|---|
| `PENDING` | 已受理派发，投递尚无结果 | 否 | 派发路径（**新增**） |
| `SUCCESS` | 投递成功（HTTP 2xx） | 是 | 重试循环结束后的原地更新 |
| `FAILED` | 投递失败（重试耗尽 / URL 被拒 / 中断残留） | 是 | 同上，或启动清扫 |

### 1.3 不变量

| # | 不变量 | 由什么保证 | 违反后果 |
|---|---|---|---|
| **INV-1** | 一次投递**恰好一条**记录（不因"先插后更"变成两条） | 派发时插入、结束时 `updateById` 原地更新，插入点全仓**仅一处** | 记录重复，投递统计翻倍 |
| **INV-2** | 记录**存在性**不依赖投递是否完成 | 派发即插入 | 在飞不可见；进程中断则记录彻底丢失（本规格修的就是这个） |
| **INV-3** | 不存在**永远悬空**的 `PENDING` | 启动清扫按时间阈值判定残留为 `FAILED` | 只是把"记录丢失"换成"记录永远在途" |
| **INV-4** | 终态**不被回退**为 `PENDING` | 写入路径单向（派发→终态） | 状态反复，前端闪烁 |

### 1.4 INV-3 的时间阈值设计（含假设）

**假设**：本服务按**单实例**部署（仓库内无集群/多实例的证据）。

**阈值语义**：清扫只处理 `created_at` 早于「最长退避总和 + 余量」的 `PENDING` 行，**不是**"启动时无条件清空全部 `PENDING`"。

**为何这样取**：多实例部署下，另一个实例可能**确有**在途投递；无条件清扫会把它误判为失败——即制造一个新的"记录不反映真实"。带时间阈值则在单实例与多实例下都正确。这是刻意的**保守取向**：宁可让极少数残留多停留一个启动周期，也不误伤真实在途记录。

**边界**：正常投递最长约 36 秒（退避 1s / 5s / 30s）。阈值须**显著大于**该值，留有充分余量，避免把"刚好还在重试"的记录判死。

### 1.5 与既有列的关系

| 列 | 本规格是否改动 | 说明 |
|---|---|---|
| `status` | **取值集合扩大**（新增 `PENDING`），列定义不动 | 无迁移，见 §0 |
| `created_at` | 不动 | 清扫的判定依据 |
| `updated_at` | 不动 | 由数据库维护（`ON UPDATE CURRENT_TIMESTAMP`） |
| 重试次数 / HTTP 状态 / 错误摘要 | 若列已存在则填充；**若需新列则触发 FR-V14 范围守卫，必须停下重新裁决** | 见 plan.md 的复杂度登记 |

> **登记一处观察（不在本规格范围）**：`status` 列的默认值是 `'SUCCESS'`。一条未显式给状态的插入会**自称成功**。本规格不处理（改默认值需迁移，且影响历史数据解读），仅登记。

## 2. 语义模型：乐观锁令牌（`user.version`）

### 2.1 令牌的语义边界

`BaseEntity.version` 是一个**并发编辑令牌**：它回答"我读到的这一行，在我写回之前有没有被别人改过"。

```
   管理端读到 user(id=7, version=3)
                │
                ├── 目标用户登录（本规格修复点）
                │        └─► 修复前：version 3 → 4（令牌被消费）
                │            修复后：version 保持 3
                │
                └── 管理端提交编辑（携带 version=3）
                         └─► 修复前：WHERE version=3 不匹配 → 409 VERSION_CONFLICT（误报）
                             修复后：匹配 → 编辑成功
```

### 2.2 规则

| # | 规则 | 理由 |
|---|---|---|
| **R-1** | **读语义的操作不得消费令牌**（登录、查看、导出等） | 多人同时登录并无冲突；令牌保护的是编辑冲突 |
| **R-2** | 定向字段更新**不得**经过实体级 `updateById` | 实体非空且带 `@Version` 时插件才介入；定向更新（实体为 `null`）不产生版本自增 |
| **R-3** | 定向更新**只写目标列** | 顺带消除一整类丢更新：原写法把整行回写，`passwordHash`/`role`/`enabled` 等他人改动会被静默覆盖 |
| **R-4** | 真正的业务编辑**仍须**参与乐观锁（FR-V02） | 令牌不能因此被架空——那两个 IT 用例正是回归的守卫 |
| **R-5** | 定向更新后 `updated_at` **不陈旧** | 由**数据库**维护（`V1__init.sql:15` 的 `ON UPDATE CURRENT_TIMESTAMP`），不依赖应用层填充 |

### 2.3 副作用面（已核查）

仓库内**不存在第二处**"读实体 → 改一个非业务字段 → `updateById`"的路径。唯一的同类语义点是 `UserService.java:136`（管理端编辑时**显式**回填 `req.getVersion()`）与 `:179/:199`（令牌版本递增）——前者正是乐观锁的**正确用法**，后者是**有意的业务更新**，**均不动**。

## 3. 映射模型：校验失败 → HTTP 状态

### 3.1 现状（缺陷）

同一个关闭端点，两条失败路径给出**不同**的状态码：

| 输入 | 拦截者 | 返回 | 契约要求 |
|---|---|---|---|
| `closeResult` 缺失 / 空白 | `@NotBlank`（Bean Validation） | **400** | 422 |
| `closeResult` = `"MAYBE"`（非空但非法） | Service 的领域校验 | **422** `CLOSE_RESULT_REQUIRED` | 422 |

**这不是"契约比实现严格"，而是实现自相矛盾**——同一语义的两种输入给出两种状态码。

### 3.2 目标映射（FR-V03 / FR-V15）

| 违规类型 | 判定键 | 状态码 | 错误码 |
|---|---|---|---|
| 关闭端点 `closeResult` 违规 | 绑定目标是 `CloseRequest` **且** 违规字段是 `closeResult` | **422** | `CLOSE_RESULT_REQUIRED`（**既有**错误码，不新增） |
| **其他一切** DTO 校验违规 | 兜底 | **400** | `BAD_REQUEST`（**不变**） |

### 3.3 判定键的选择理由

用**绑定目标 DTO 类型 + 字段名**，而非 URI 或路径匹配：

- **显式** —— 读代码即知影响面，不受路由改名影响；
- **天然限定** —— 只可能命中这一个端点，FR-V15（其他端点仍 400）由构造本身保证，并由一个**行为测试**钉住。

### 3.4 分层归属

| 关注点 | 归属层 | 说明 |
|---|---|---|
| "结果必填且必须是 WON/LOST"（业务规则） | **Service** | 保留不动，作第二道防线 |
| "该约束违反应映射为何种 HTTP 状态码"（HTTP 关注点） | **表现层**（异常处理器） | 章程原则二明确把 HTTP 关注点划给表现层 |

**禁止**：不得把业务判断挪进异常处理器。异常处理器只做**映射**，不做**判定**。

## 4. 前端展示模型：投递状态的第三态

`IntegrationHubPage.tsx:195` 当前是**二元**渲染（`status === 'SUCCESS'` ? 绿"成功" : 红"失败"）——**任何非 `SUCCESS` 的值都会被渲染成红色"失败"**。

| 后端 `status` | 修复前前端渲染 | 修复后前端渲染（FR-V13） |
|---|---|---|
| `SUCCESS` | 绿 / 成功 | 绿 / 成功（不变） |
| `FAILED` | 红 / 失败 | 红 / 失败（不变） |
| `PENDING` | **红 / 失败**（错误！） | **中性色 / 投递中**（新增分支） |

**必要性**：若只改后端，一条正在投递中的记录会被前端**报成失败**——等于把本规格刚修掉的"记录不反映真实"原样搬到界面上。第三态取色参照既有先例 `ExportCenterPage.tsx:40` 的 `'processing'`。

**约束**：新增 i18n 键**必须中英文同步**，否则 `pnpm run i18n:check`（键数对齐门禁）转红。该门禁是 083 登记的六道前端门禁之一。

**影响面**：全仓**仅此一处**渲染投递状态（其余 `SUCCESS`/`FAILED` 匹配点属于数据保留与导出两个不同功能，不受影响）。
