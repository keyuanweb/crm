# 研究记录：验证门禁转绿（085）

本文件记录 planning 前的**决策及其依据**。每条都含"决策 / 理由 / 备选及其被否原因"，且**依据均为本轮实读代码所得**（含文件与行号），不是推测。

## R1 —— 登录为何会污染乐观锁令牌，以及怎么修

**事实**：`AuthService.java:89-91` 为更新"最后登录时间"执行 `user.setLastLoginAt(now); userMapper.updateById(user);`，而 `user` 是刚从库里读出的完整实体。`BaseEntity.java:23` 声明了 `@Version private Integer version = 0;`，MyBatis-Plus 的乐观锁插件因此在这次 `updateById` 上生效，生成 `SET version = version + 1 WHERE id = ? AND version = ?`。

**后果**：登录——一个**读语义**的操作——把该用户对外的版本标识推高。任何在登录前读到该用户的管理端页面，提交时携带的版本标识即刻过期，得到 409。命中路径：管理端打开用户列表 → 目标用户登录 → 管理端编辑该用户。

**决策**：把"更新最后登录时间"改为**定向更新**，不经过实体级 `updateById`：以 `update(null, LambdaUpdateWrapper...eq(id).set(lastLoginAt, now))` 只写这一列。实体为 `null` 时乐观锁插件不介入，故不产生版本自增。

**理由**：
- 登录**不是**一次业务编辑，它不应参与"谁改得更晚"的并发判定——乐观锁保护的是编辑冲突，而多个人同时登录并无冲突可言。
- 定向更新还有一个附带好处：它**不再把整行回写**。原写法把 `passwordHash`、`role`、`enabled` 等全部字段一并写回，任何"读后到写前"的他人改动都会被静默覆盖（本身就是一类丢更新）。
- **不会留下陈旧时间戳**：`user.updated_at` 在 `V1__init.sql:15` 定义为 `ON UPDATE CURRENT_TIMESTAMP`，由**数据库**维护，不依赖应用层的自动填充。

**备选与否决**：
- **保留 `updateById` 但把 `version` 置空**：能绕过乐观锁，但依赖"字段为 null 时插件跳过"这一隐式行为，且仍然整行回写。可读性与稳健性都更差。
- **给 mapper 加一个 `@Update` 手写方法**：同样可行且更显式，但引入一处裸 SQL；而定向更新用框架 API 即可表达，符合章程原则五"从最简设计开始"。
- **关掉乐观锁插件**：不可接受——它同时保护着所有真正的并发编辑，本规格的验收场景之一正是要求它继续有效（FR-V02）。

**副作用面**：需确认仓库内**没有第二处**"读实体 → 改一个非业务字段 → `updateById`"的路径。目前已知的同类语义点（`UserService.java:179/199` 的令牌版本递增）是**有意的业务更新**，那正是乐观锁该管的事，不动。

## R2 —— 400 从哪来，以及怎么让它变成契约约定的 422

**事实链**（三条，缺一不可）：
1. `SalesOpportunityController.java:91` 的关闭端点声明 `@Valid @RequestBody CloseRequest`；
2. `CloseRequest.closeResult` 带 `@NotBlank`（`CloseRequest.java:10-12`），故**请求体缺结果时 Bean Validation 先行拦截**；
3. `GlobalExceptionHandler.java:31-38` 的 `handleValidation` **把这一类异常硬编码为 400**，于是线上得到 400。

而契约（`001-crm-core/contracts/sales-opportunities.md:81`）写的是 **422 `CLOSE_RESULT_REQUIRED`**。

**加强证据（本轮新发现）**：`SalesOpportunityService.java:138-141` **已经**在抛 `ErrorCode.CLOSE_RESULT_REQUIRED`（`ErrorCode.java:29`，状态码 422）。也就是说**同一个端点**对「结果非法」（如 `"MAYBE"`）返回 **422**，对「结果缺失」返回 **400**——**两条失败路径语义不一致**。这不是"契约写得比实现严格"，而是实现自身自相矛盾。

**决策（对应 Q1 裁决 B）**：在 `handleValidation` 中增加一个**按 DTO 类型与字段限定**的分支——当绑定目标是 `CloseRequest` 且违规字段是 `closeResult` 时，返回 **422 + `ErrorCode.CLOSE_RESULT_REQUIRED`**；其余一切保持 400。`@NotBlank` **保留**。

**理由**：
- **同时满足章程两条不可协商原则**：原则三要求 DTO 声明校验约束（保留注解），原则一要求实现遵从契约（线上回到 422）。
- 判定键用**DTO 类型**而非 URI 或路径匹配：显式、不受路由改名影响，且天然"只影响这一个端点"。
- 服务层的判空与 `WON/LOST` 校验**原样保留**，作为第二道防线；不因边界层修好就删掉。

**备选与否决**：
- **去掉 `@NotBlank`**（原方案 A）：最简洁，但与原则三"所有 DTO 必须声明 Jakarta Bean Validation 约束"字面相抵，需走偏差批准。既然存在同时满足两条原则的写法，就不应选择牺牲其一。
- **全局把 400 改成 422**：**绝对不可**。会污染所有端点的失败语义，制造比原缺陷更大的问题。这正是 FR-V15 要钉住的。
- **改契约把 422 写成 400**：违背原则一，且既有调用方为 `CLOSE_RESULT_REQUIRED` 写的分支会失效。

**分层归属说明**（应对原则二的审查）：这段映射放在 `GlobalExceptionHandler`（表现层）而非 Service，是**正确**的分层——"某个边界校验失败应映射为何种 HTTP 状态码"是纯粹的 **HTTP 关注点**，原则二明确把"Controller 只处理 HTTP 关注点"划给表现层。业务规则（"结果必填且必须是 WON/LOST"）仍在 Service。**不得**把它做成"把业务判断挪进异常处理器"。

## R3 —— 投递记录为何要等 36 秒，以及新形态的两个配套问题

**事实**：`WebhookDeliverer.java:72-102` 的重试循环（退避 1s/5s/30s）结束后，才在第 103 行调用 `record(...)` 落库；`record`（`:142-168`）只做 `deliveryMapper.insert(d)`。故：①投递最长 36 秒内在页面上**不可见**；②若进程在此窗口内终止，该条投递**永远不会**出现；③第 4 例集成测试失败（`IntegrationHubIT.integrationHub` 等 1.5 秒，记录要 36 秒才出现）正是它的外部表现。

**决策（对应 Q2 裁决 A）**：**派发时先插入一条 `PENDING` 记录**，重试循环结束后**原地更新**（`updateById`）为终态（`SUCCESS`/`FAILED`），带上重试次数、HTTP 状态与错误摘要。

**理由**：把"记录的事实"与"投递的结果"解耦——记录从**派发**那一刻就存在，这既是可观测性的正确语义，也让第 4 例用例**无需改动**即通过（修对了根因，用例自然绿，这本身就是证据）。

**新形态带来的两个必须配套解决的问题**：

1. **中断残留的归宿（FR-V07）**：一条 `PENDING` 记录若因进程终止而永不更新，就会永远悬空——那只是把"记录丢失"换成了"记录永远在途"。**决策**：应用启动时做一次清扫，把 `created_at` 早于"最长退避总和 + 余量"的 `PENDING` 行判定为 `FAILED`（带明确原因）。**为何带时间阈值而非"启动时全部清扫"**：多实例部署下，另一个实例可能确有在途投递，无差别清扫会误伤。带阈值则在单实例与多实例下都正确。**假设**：本服务当前按单实例部署（无集群证据）；阈值设为时间窗而非精确判定，是刻意的保守取向。
2. **一次投递只对应一条记录（FR-V08）**：`webhook_delivery` 的 id 由数据库生成，而 `mybatis-plus.global-config.db-config.id-type: auto`（`application.yml:93`）保证 `insert` 后实体带上生成的 id，可用于后续 `updateById`。**这一点已核实**，不需要迁移。

**备选与否决**：
- **维持现状、只把用例等待改到 40 秒**（原方案 B）：改动最小，但**保留**"在飞不可见"与"进程中断即丢失"两个缺陷——等于承认记录可以静默丢失，与 083 刚交付的 T078（对外记成功、实际未执行）属**同一类诚信缺口**。本规格的母规格把这一类列为零容忍，故不可接受。

## R4 —— 新增 `PENDING` 是否构成契约变更？（结论：不构成）

**事实**：两份相关契约都**没有枚举**投递记录的状态取值：
- `058-integration-hub/contracts/integration-hub.md:26-30` —— 只写"该通道推送记录（复用 webhook_delivery）"；
- `055-open-platform/contracts/open-platform.md:38-40` —— 只写"推送记录分页"。

**决策**：**不修改任何契约**，故本规格**不产 `contracts/`**（与 003、083 的"加固类不产契约"先例一致）。新增的状态取值由一个测试钉住（FR-V13），以满足原则一"每次契约变更都必须附带一个测试"的**精神**（即便此处严格说不是契约变更）。

**同时确认无需迁移**：`webhook_delivery.status` 是 `VARCHAR(20) NOT NULL DEFAULT 'SUCCESS'`（`V63__open_platform.sql:42`），**不是 ENUM**，且该表此后无任何 `ALTER`。故新增取值**不涉及 schema 变更**，FR-V14 成立。

> **顺带记下一处观察（不在本规格范围内，不擅自扩大）**：该列的默认值是 `'SUCCESS'` —— 一条没显式给状态的插入会自称成功。这与本规格刚修的那类"记录不反映真实"同源。本规格不处理它（改默认值需要迁移，且会影响历史数据的解读），仅登记。

## R5 —— 新增状态值在前端会被渲染成"失败"（FR-V13 的真实风险）

**事实**：`IntegrationHubPage.tsx:195` 的渲染是二元的——
```
r.status === 'SUCCESS' ? <Tag color="green">成功</Tag> : <Tag color="red">失败</Tag>
```
即**任何非 `SUCCESS` 的值都显示为红色"失败"**。若只改后端，一条正在投递中的记录会被前端**报成失败**——等于把本规格刚修掉的"记录不反映真实"原样搬到界面上。

**决策**：前端补第三态分支（如"投递中"，按 `ExportCenterPage.tsx:40` 已有的 `'processing'` 先例取蓝/处理中色），并补齐中英文两个 i18n 键。

**理由与约束**：
- 全仓只有**这一处**渲染投递状态（已核实：其余 `'SUCCESS'`/`'FAILED'` 匹配点属于数据保留与导出两个不同功能，不受影响）。
- 新增 i18n 键**必须**中英文同步，否则 `pnpm run i18n:check`（键数对齐门禁）会红。该门禁是 083 登记过的六道前端门禁之一，不能为了本规格把它弄红。

**备选与否决**：**只在后端改、前端下一版再说**——不可接受。那会让修复上线后立刻产生一个**新的**用户可见错误（在途显示为失败），比原缺陷更误导。

## R6 —— 环境噪声：开发后端会伪装成"构建失败"

**事实**（本轮实测踩到）：在开发后端进程正在运行的机器上执行完整构建校验，会在打可执行包一步失败——`spring-boot:repackage` 无法把 `target/crm-backend-0.1.0-SNAPSHOT.jar` 重命名为 `.jar.original`，因为**该进程持有这个文件**（Windows 不允许重命名被占用的文件）。错误信息是 `PluginExecutionException`，**离根因很远**。

**后果**：本轮第一次基线跑**根本没跑到集成测试**（surefire 551 例全绿后即中止）。若不加辨别，会把环境噪声误读成"代码缺陷"，或反过来把"没跑到集成测试"误读成"集成测试通过"。

**决策**：验收与取证时以**跳过打可执行包**的方式执行完整构建校验，并在记录中写明所用命令与理由。这一条写入 `spec.md` 的「假设」与 `quickstart.md`，作为**验收纪律**。

**同时确认**：`jacoco:prepare-agent` 与 `jacoco:report` 在该次构建中**正常执行**（日志含 `Loading execution data file`，非 `Skipping`），故本规格不涉及 083 记录过的那个 `-DargLine` 陷阱；`jacoco:check` 之所以零命中，是因为 `failsafe:verify` 先失败中止——与本规格的判断一致。
