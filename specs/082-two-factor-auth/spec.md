# 功能规格：双因素认证（Two-Factor Authentication / TOTP）

**功能分支**: `082-two-factor-auth`

**创建日期**: 2026-09-11

**状态**: 草稿

**输入**: 当前系统仅支持「用户名 + 密码（+ 可选图形验证码）」单因素登录，`CRM_FEATURE_COMPARISON.md` 第四节将 2FA/MFA 列为安全合规缺口。本模块为账号增加基于 TOTP（RFC 6238，Google Authenticator / Microsoft Authenticator / 1Password 等兼容）的第二因素，并提供一次性恢复码，覆盖企业合规与账号盗用防护需求。

## 用户场景与测试（必填）

### 用户故事 1 - 已绑定用户的二次验证登录（优先级：P1）

已启用 2FA 的用户输入账号密码后，系统不再直接签发令牌，而是要求输入认证器 App 中的 6 位动态码；校验通过后才签发访问令牌。

**为什么优先**: 这是 2FA 的核心安全价值所在——没有它，绑定流程毫无意义；也是唯一能独立上线即产生防护效果的切片。

**独立测试**: 为测试账号启用 2FA → 用正确密码登录 → 确认被要求输入动态码 → 输入正确动态码 → 成功进入系统。

**验收场景**:

1. **Given** 用户已启用 2FA，**When** 提交正确的用户名与密码，**Then** 响应不包含 `accessToken`，而是返回 `mfaRequired: true` 与短期 `mfaToken`，前端跳转验证视图。
2. **Given** 已获得 `mfaToken`，**When** 提交当前有效的 6 位动态码，**Then** 返回 `accessToken` 与 `refreshToken`，正常进入系统。
3. **Given** 已获得 `mfaToken`，**When** 提交错误动态码，**Then** 返回 401 且提示剩余尝试次数，不签发令牌。
4. **Given** 未启用 2FA 的用户，**When** 登录，**Then** 行为与现状完全一致（直接签发令牌），不受本模块影响。
5. **Given** 同一动态码已被成功使用，**When** 在同一 30 秒时间窗内重复提交，**Then** 拒绝（防重放）。

---

### 用户故事 2 - 启用 2FA 的绑定向导（优先级：P1）

已登录用户在账户安全页发起绑定：系统展示密钥二维码（可手动输入），用户用认证器扫码后输入一次动态码完成校验，系统返回一次性恢复码。

**为什么优先**: 没有绑定入口，用户无法开启该能力；且绑定必须与登录校验同时交付才构成闭环。

**独立测试**: 进入账户安全页 → 点击启用 → 扫码 → 输入动态码 → 状态变为「已启用」并展示恢复码。

**验收场景**:

1. **Given** 已登录用户未启用 2FA，**When** 点击「启用双因素认证」，**Then** 返回 Base32 密钥、`otpauth://` 链接与二维码图片，且此时账号仍处于未启用状态。
2. **Given** 已获取密钥，**When** 输入认证器中当前显示的 6 位码且校验通过，**Then** 2FA 状态置为已启用并返回 10 个恢复码（仅本次以明文返回一次）。
3. **Given** 已获取密钥，**When** 输入错误动态码，**Then** 绑定失败、状态保持未启用，允许重试。
4. **Given** 绑定流程未完成，**When** 用户关闭页面后重新发起，**Then** 生成新密钥并使旧密钥失效。
5. **Given** 用户已启用 2FA，**When** 再次访问启用入口，**Then** 提示已启用，仅提供「重新生成恢复码」与「关闭 2FA」。

---

### 用户故事 3 - 恢复码登录（优先级：P2）

用户丢失认证器设备时，可用启用时保存的一次性恢复码完成二次验证登录。

**为什么优先**: 这是防止用户被永久锁死在自己账号外的必要逃生通道，但可在核心链路之后交付。

**独立测试**: 使用未使用的恢复码完成二次验证 → 成功登录 → 该恢复码不可再次使用。

**验收场景**:

1. **Given** 用户在验证视图选择「使用恢复码」，**When** 提交某个未使用的恢复码，**Then** 校验通过并签发令牌，同时该恢复码被标记为已使用。
2. **Given** 某个恢复码已被使用过，**When** 再次提交，**Then** 拒绝。
3. **Given** 用户剩余恢复码数量 ≤ 2，**When** 查看账户安全页，**Then** 展示剩余数量并提示重新生成。
4. **Given** 恢复码全部用完，**When** 再次尝试恢复登录，**Then** 提示需联系管理员重置。

---

### 用户故事 4 - 关闭 2FA 与管理员重置（优先级：P2）

用户凭密码 + 当前动态码（或恢复码）关闭 2FA；管理员可为遗忘设备的用户重置 2FA。

**为什么优先**: 无法关闭会造成运维死结，管理员重置是企业环境的兜底手段。

**独立测试**: 用户输入密码 + 动态码关闭 2FA → 下次登录不再要求动态码。

**验收场景**:

1. **Given** 用户已启用 2FA，**When** 提交正确密码 + 有效动态码或恢复码，**Then** 2FA 关闭、密钥与恢复码作废，并记录审计日志。
2. **Given** 用户已启用 2FA 但密码错误，**When** 尝试关闭，**Then** 拒绝并提示密码错误。
3. **Given** 管理员在用户管理页对某用户执行「重置 2FA」，**When** 确认，**Then** 该用户的 2FA 被关闭且恢复码作废，并记录审计日志（操作人 = 管理员）。
4. **Given** 2FA 已关闭的用户，**When** 登录，**Then** 直接签发令牌。

---

### 用户故事 5 - 强制策略（优先级：P3，本期仅预留设计）

管理员可将 2FA 设为对指定角色强制要求，未绑定用户在登录后被引导（或强制）完成绑定。

**为什么优先**: 合规场景需要，但依赖 1~4 已稳定运行，且涉及登录流程分支增多，作为后续增量。

**独立测试**: 开启角色强制策略 → 该角色未绑定用户登录后被要求绑定 → 绑定完成才可进入系统。

**验收场景**:

1. **Given** 策略对 `ADMIN` 强制，**When** 未绑定的管理员登录，**Then** 返回 `mfaSetupRequired: true` 并引导至绑定向导（本期评估是否启用，见「假设」）。

### 边界情况

- **客户端时间漂移**：认证器与服务端时间偏差允许 ±1 个时间步（即 ±30 秒窗口）。
- **动态码重放**：同一用户在同一时间步内已使用过的动态码不得再次通过校验。
- **连续失败**：同一用户连续 5 次二次验证失败后锁定 15 分钟（期间即使密码正确也拒绝并提示稍后再试）。
- **票据过期**：`mfaToken` 有效期 5 分钟且一次性消费；过期或重复使用返回 401 并要求重新走密码登录。
- **密码阶段已失败**：图形验证码（017）与 2FA 的叠加顺序为「用户名 + 密码 + 图形验证码 → 2FA 动态码」，前序失败不消耗 2FA 失败计数。
- **Redis 不可用**：`mfaToken` 与限流计数依赖 Redis；Redis 不可用时拒绝已启用 2FA 用户的登录（失败关闭，不得静默降级为单因素）。
- **密钥保护**：TOTP 密钥必须以加密形式落库，任何接口（含 `GET`）都不得回显明文密钥（绑定流程中的一次性返回除外）。
- **绑定中途放弃**：未完成校验的密钥不得使账号进入「已启用」状态，也不影响下一次登录。
- **管理员自身**：管理员重置他人 2FA 需具备 `user:manage` 权限；不得通过重置接口绕过密码阶段。

## 需求（必填）

### 功能需求

- **FR-M01**: 系统必须支持基于 TOTP（RFC 6238，HMAC-SHA1，6 位，30 秒步长）的动态码校验，时间窗容差 ±1 步。
- **FR-M02**: 用户登录时若已启用 2FA，系统必须暂缓签发令牌，改为返回 `mfaRequired: true` 与一次性 `mfaToken`（TTL 300 秒，Redis 存储）。
- **FR-M03**: 系统必须提供服务端生成的二维码（PNG Base64）与 `otpauth://` 链接，供认证器扫描或手动录入。
- **FR-M04**: 绑定必须经「生成密钥 → 输入动态码校验」两步完成；校验通过前账号不得进入已启用状态。
- **FR-M05**: 启用成功时系统必须生成 10 个一次性恢复码，明文仅在生成响应中返回一次，落库仅存哈希。
- **FR-M06**: 恢复码必须一次性有效，使用后立即失效，且可在账户安全页重新生成（重新生成使旧码全部失效）。
- **FR-M07**: 系统必须限制二次验证失败次数（连续 5 次失败锁定 15 分钟），并在响应中返回剩余尝试次数。
- **FR-M08**: 系统必须防止同一时间步内动态码重放。
- **FR-M09**: 用户必须能以「密码 + 动态码或恢复码」自行关闭 2FA，关闭后密钥与恢复码作废。
- **FR-M10**: 管理员必须能对指定用户重置 2FA（关闭并要求重新绑定），此操作记录审计日志。
- **FR-M11**: TOTP 密钥必须加密存储（AES-256-GCM），密钥材料来自外部配置项，不得硬编码。
- **FR-M12**: 系统必须记录 2FA 启用、关闭、重置、校验失败等安全事件到审计日志。
- **FR-M13**: 账户安全页必须展示 2FA 状态、绑定时间与剩余恢复码数量。
- **FR-M14**: 未启用 2FA 的既有用户，登录与令牌签发行为必须与现状完全一致（零回归）。
- **FR-M15**: 所有新增文案必须提供中文与英文两份资源。

### 关键实体（涉及数据）

- **User 扩展字段**: 是否启用 2FA、加密后的 TOTP 密钥、绑定时间、最近一次二次验证时间。
- **UserRecoveryCode**: 一次性恢复码（所属用户、码哈希、是否已使用、使用时间、创建时间）。
- **MfaTicket（Redis）**: 密码校验通过后的短期二次验证票据（票据值 → 用户 ID，TTL 300 秒，一次性）。
- **MfaAttemptCounter（Redis）**: 按用户维度的失败计数与锁定截止时间。
- **UsedTimeStep（Redis）**: 已消费的动态码时间步，用于防重放。

## 成功标准（必填）

### 可度量结果

- **SC-M01**: 已启用 2FA 的用户完成「密码 → 动态码」全流程 ≤ 30 秒。
- **SC-M02**: 绑定流程 ≤ 3 步（扫码/录入密钥 → 输入动态码 → 保存恢复码），首次成功率 ≥ 90%（含 ±1 步时间容差）。
- **SC-M03**: 未启用 2FA 用户的登录接口响应时间与现状相比无退化（P95 增幅 ≤ 50 ms）。
- **SC-M04**: 连续错误 5 次后锁定生效，第 6 次即使动态码正确也被拒绝，锁定期满后自动恢复。
- **SC-M05**: 动态码重放与恢复码重用在自动化测试中 100% 被拒绝。
- **SC-M06**: 密钥密文落库，数据库中不存在任何明文 TOTP 密钥（人工抽查 + 单测断言）。
- **SC-M07**: 后端 `mvn test`（含新增 MfaService 单测与 AuthMfaIT 集成测试）通过；前端 `pnpm run typecheck && pnpm run lint && pnpm run test` 通过。
- **SC-M08**: 未启用 2FA 的既有前端测试 58 项全部保持通过（零回归）。

## 假设

- 用户持有支持 TOTP 的认证器 App（Google/Microsoft Authenticator、1Password 等），系统不内置认证器。
- 系统时间以服务器为准，允许客户端 ±1 步漂移；不做 NTP 校时功能。
- Redis 为登录链路的强依赖（当前架构已如此，见 017 图形验证码）。
- 恢复码以「10 个 8 位 Base32 字符」形式呈现，用户自行保存；系统不提供短信/邮件找回。
- **用户故事 5（强制策略）本期仅保留设计与契约扩展点，不实现**；实现与否取决于后续合规需求。
- 2FA 仅作用于主站登录，不改变开放平台 API Key 与 Webhook 的既有鉴权方式。

### 一、恢复码的字母表（本条同时是**原文自相矛盾**的订正）

**原文（保留）**：`## 假设` 第 4 条「恢复码以『10 个 8 位 **Base32** 字符』形式呈现」。

**订正**：措辞应为「10 个 **8 位无歧义字符**」。理由是**契约自己给出的样例就不满足 Base32**：
`contracts/auth-mfa.md` 的 `enable` 响应样例里有 `"23456789"` 与 `"6789BCDF"`，
含 `8` 与 `9` 两个字符，而 **标准 Base32 字母表（RFC 4648）不含 `8`/`9`**
（只到 `2-7`）。⇒ 两处互斥，必有一处错，实测以契约为准。
真实字母表取仓库既有的 `CaptchaService.CHARS` = `ABCDEFGHJKMNPQRSTUVWXYZ23456789`
（**31 个符号**，剔除易混的 `I`/`L`/`O`）——与图形验证码（017）同源，用户抄写时不会在 `0/O`、`1/I/l` 上出错。
**这不是放宽要求，是收紧**：Base32 的 `A-Z2-7` 里 `I`/`L`/`O`/`0`/`1` 都可打印，抄写歧义更大。

### 二、SC-M08 的「58 项」是陈旧计数

**原文（保留）**：`SC-M08`「未启用 2FA 的既有前端测试 **58 项**全部保持通过（零回归）」。

**订正**：实测为 **86 个测试文件 / 429 个用例**（`git ls-tree -r --name-only HEAD | grep -Ec 'frontend/src/.*\.test\.tsx?$'`）。
**判据本身（零回归）不变，只是基数要按实测重算**。同一处陈旧计数另见 `plan.md` 第 12 步与 `tasks.md` T028。

### 三、US5 的 `mfaSetupRequired` **本期不落地为字段**

**原文（保留）**：US5 验收场景 1「返回 **`mfaSetupRequired: true`** 并引导至绑定向导」，及
`## 假设` 末段「本期仅保留设计与契约扩展点」。

**订正**：US5 本期不实现这一条**不变**；但「预留扩展点」的**形态**由「先加一个恒为 `null` 的响应字段」
**改为**「服务端留一个单方法钩子 `MfaChallengeService.challengeFor(user) → Optional<MfaChallenge>`」。
即**不新增 `mfaSetupRequired` 字段** —— 没有任何代码会写它，加了就是**死 JSON**（088 刚清掉一批真孤儿，本仓口径是不再新造）。
将来要加该字段时**不构成破坏性变更**：`application.yml:22` 的 `spring.jackson.default-property-inclusion: non_null`
会让 `null` 字段整个不出现在响应里，故加字段不改变既有响应的字节。
US5 的唯一改动点因此收敛到 `MfaChallengeService` 的**那一个方法**。

### 四、Redis 不可用的错误码

**原文（保留）**：边界情况「**Redis 不可用**：…拒绝已启用 2FA 用户的登录（失败关闭，不得静默降级为单因素）」。

**订正**：**需求语义一字不改**（仍为 fail closed）。此处只补一条**实现层事实**：
原 `ErrorCode` 枚举里**没有任何 503/「依赖不可用」码**，故新增 `MFA_STORE_UNAVAILABLE`(503)
作为该边界情况的**可观测出口**；同时新增 `MFA_LOCKED`(429)。二者都是**新增**，不改动既有码的语义。
错误码全集见 `plan.md` 的订正块（原计划的 8 个码里 `MFA_REQUIRED` 是死数据，见该处 §二）。
