### 2.1 机械转译约定（镜像的实际执行规则）

镜像**不得语义重写**：只做方言转译，取值、列序、约束名、索引名逐字保留。下表按**实测**与既有 76 张镜像表比对得出，共三类差异。

**（一）类型差异**

| 生产（MySQL） | 镜像（H2，`MODE=MySQL`） |
|---|---|
| `BIGINT NOT NULL AUTO_INCREMENT` + 独立 `PRIMARY KEY (id)` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `DATETIME` | `TIMESTAMP` |
| `TEXT` | `CLOB` |
| `JSON` | `CLOB`（与既有 JSON 载荷列一致；H2 无 `JSON` 关键字先例） |
| `TINYINT(1)` | `INT` |

**（二）子句差异**——以下子句**一律省略**，与既有 76 张镜像表形制一致：

- `CONSTRAINT fk_... FOREIGN KEY ...` —— 全文件 **0 个外键**，这是既有约定
- `COMMENT '...'`
- `ON UPDATE CURRENT_TIMESTAMP`
- `ENGINE=... CHARSET=...`、`IF NOT EXISTS`
- 内联 `INDEX x (col)` → 改为独立的 `CREATE INDEX x ON t (col);`

**（三）标识符可用性差异** —— **本条为实施期补入，原约定表遗漏**

MySQL 的**非**保留字可能是 H2 的**保留字**。此时镜像必须为该标识符补引号；引号形式沿用既有约定——**反引号**（见 `user` 表：`CREATE TABLE \`user\``、`CREATE INDEX ... ON \`user\` ...`，因 `user` 在两个方言中都是保留字，故生产 DDL 本就有引号可直接沿用）。

- **已实测命中：`year`**（`sales_quota.year`）。生产 `V71__sales_quota.sql:8` 裸写 `year INT NOT NULL`，MySQL 接受；H2 报 `expected "identifier"`。**未加引号时整个上下文加载失败**——`DataSourceInitializationConfiguration` 是 `userMapper` 的依赖，级联致 26 个"错误"，而非单例失败。
- **同批未命中**：`quarter` 不是 H2 保留字，故不加引号（H2 也只报了 `year`）。
- **判别方式**：不可凭"生产 DDL 没加引号"推断 H2 也不必加。新镜像后必须**实际加载一次上下文**（跑一次集成测试）——`SchemaParityIT` 只比对版本号集合、不解析 SQL 文本，**守卫转绿不能证明 schema 可执行**（见 baseline.md §5.1）。

## 3. 进程内缓存结构

缓存必须为**进程内**实现，理由见 research.md §4。键与值按被缓存方法的真实签名确定：

| 缓存 | 键 | 值 | TTL | 失效点 |
|---|---|---|---|---|
| 角色权限 | 角色编码（`permissionsOf(String roleCode)`） | 权限码列表 | **60 秒** | 角色新建 / 修改 / 删除（含角色权限变更）——`RoleService` 的 `create`／`update`／`delete` 三处写入点各调一次 `evictPermissionsCache(code)`，**按编码逐条失效即已充分** |
| 可见数据范围 | 用户 id（`resolveVisibleOwnerIds(Long userId)`） | 可见负责人 id 列表 | **30 秒** | **任何用户或部门的增删改 → 全量失效** |

> TTL 上限由 spec.md「关键实体」约束：**二者均不得超过 60 秒**。角色权限缓存取 60 秒（即上限值）；可见范围缓存取 30 秒——其值随组织成员变动，陈旧代价是越权读数据，故取更短值。

> **T062 修正（角色编码失效）**：本表原先写"角色编码本身被修改时，旧编码与新编码**同时**失效"。复核发现**该场景在设计上不存在**——`RoleService.update` 只改名称／描述／数据范围／启用位，**不接受编码变更**（`RoleService.java:213-214` 明写此约束），故不存在"旧编码"这个键需要失效。原文描述的是一个不可达路径，属**设计文档多写了一条并不存在的机制**；已改为按编码逐条失效，与代码实际行为一致。**此处更正的是文档，不是代码**——代码行为一直是正确的。该条正是"文档与实现一致性复核"要抓的那类偏差：不会导致故障，但会让后来者照着一份虚构的机制去推理。

**为什么"可见数据范围"必须全量失效**：该缓存按用户 id 为键，但其值来自该用户所属**部门的成员集合**。部门成员的变动（他人加入/离开/转岗）**无法从该用户自身的写操作推断**。若只在"该用户被修改"时失效，则一个已离开部门的用户仍会被列为可见——这是**越权读到他人数据**的方向。故宁可过度失效：用户与部门的任何写操作都清空该缓存，30 秒 TTL 作为直接改库与多实例场景的兜底。

## 5. 不变式

1. **角色权限缓存**在角色或角色权限的任何写操作后必须失效；陈旧窗口上限由 TTL 兜底，不得存在只在 TTL 到期才生效的写路径。
2. **可见数据范围缓存**是安全敏感缓存：任何用户或部门写操作必须全量失效。宁可过度失效，不可漏失效。
3. **出站校验无旁路**：所有出站地址的入口（通知通道、回调）统一经过同一校验器，不存在绕过路径；重定向后的最终地址同样受限。
4. **密钥主体不得满足"无限制"判定**：`isUnrestricted()` 对密钥主体恒为假。同时**保留"无主体"分支**（服务于系统内部调用），该分支不得因本次改动被收紧。
5. **测试库镜像与迁移序列一致**：由守卫测试（FR-G07）强制，新增迁移未同步镜像时构建失败——这是本规格修复不随后续版本再次失效的唯一手段。
6. **测试隔离**：每个集成测试用例开始前清空全部进程内缓存，用例结果不依赖执行顺序。
7. **前端凭据一致性**：所有 API 客户端从同一处（`accessToken`）读取凭据；收口后这三个模块的响应解析保持**裸响应体**语义，不引入全站错误信封。
