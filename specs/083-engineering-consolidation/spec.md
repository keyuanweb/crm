# 功能规格：工程收口与质量门禁修复

**功能分支**: `083-engineering-consolidation`

**创建日期**: 2026-09-12

**状态**: 草稿

**输入**: 全面的代码与工程配置审查结果——三个独立的质量门禁（集成测试执行、后端覆盖率、前端 Lint/覆盖率/E2E）全部**名义存在而实际失效**，同一根因是"机制建了但未在后续 40 余个 spec 上回填"；另有测试库镜像滞后七个版本、5 项鉴权缺陷、6 项性能与一致性损耗、14 个页面凭据失配、容器编排三处缺陷。

## Clarifications

### Session 2026-09-12

- Q: 补完测试库镜像后，如果集成测试仍因业务逻辑原因大面积失败，本规格应当怎么处置？ → A: 只清零环境类失败（表/列缺失、方言差异），业务逻辑类失败登记成清单并转入独立的集成测试修缮规格；成功标准改述为"不因环境原因失败"，不承诺构建退出码为 0。
- Q: 出站地址防护是否需要一个可配置的白名单例外？ → A: 需要。默认全部拒绝，同时提供环境变量白名单作为显式出口，与既有跨域来源配置的模式保持一致。
- Q: 实时通道允许的来源该取什么值？ → A: 复用后端已有的跨域允许来源配置（`CORS_ALLOWED_ORIGINS`），不新增独立的来源配置项，避免两处配置各自漂移。

### Session 2026-09-12（实施期修正，T062）

> 与上一节的差别：上一节是**规格定稿前**的澄清；本节记录**实施完成后**复核发现"规格文本与已交付行为不一致"的两处，按 T062 的要求回改**规格文本本身**（而非只改代码）。两处都不是"实现没做到"，而是**规格措辞比正确做法更粗**——原文对一个并非必要的手段提了要求，却没点出真正要修的缺陷。按章程原则一（契约不得被**静默**修改），此处显式记录并给出理由。

- Q: 密钥认证的状态写回，原文要求"事务化"；若实施表明**单条原子更新语句**即可达成同一目的（不丢计数、不误写授权列），以哪个为准？ → A: 以**目的**为准，不以**手段**为准。FR-G25 改写为"使用记录写回必须不丢失计数、且不得触碰授权列"，并**显式不要求** `@Transactional`（详见该条目的括注）。理由：单条 SQL 本无中间态，可回滚之物不存在；而在鉴权热路径上挂事务会延长连接与行锁持有时长，代价落在每一次开放平台调用上。**真正该修的是原文未点出的缺陷**——原实现以 `updateById` 回写整个对象（写全部非空列），于是在途鉴权能把并发 `revoke()` 刚写入的 `REVOKED` 覆盖回 `ACTIVE`。
- Q: 操作人自动填充，原文要求"新增与更新"两条路径；但**全部实体与全部迁移中均不存在 `updated_by` 列**，更新路径无从填充。如何处置？ → A: FR-G26 收窄为"实体**新增**必须自动填充操作人"；更新路径**移出本规格**（本规格不改 schema，新增该列须先做产品决策：历史数据如何回填、审计与合规导出口径是否随之改变）。**原文"操作人依赖业务代码手写"对新增成立、对更新不成立——后者是根本不存在，而非被遗漏**。

## 用户场景与测试（必填）

### 用户故事 1 - 集成测试真正执行并计入覆盖率门禁（优先级：P0）

维护者执行完整构建校验时，已编写的集成测试必须被实际执行，其覆盖率必须被计入门禁数值。

**优先级理由**: 集成测试套件已编写、已编译（60 个测试类产物已存在于编译输出目录），但**一个都不会被执行**——构建配置中没有任何集成测试执行声明，报告目录从未生成。更严重的是，覆盖率配置的注释自述"当前套件（**契约+集成+单元**）覆盖 0.36"，说明作者**以为集成测试在跑**，缺失因此长期未被发现。

实测进一步揭示该机制比预想更失效（2026-09-12，见 [baseline.md](./baseline.md)）：构建在**单元测试相位**即以 426 例中 24 失败 / 1 错误中止，**从未到达覆盖率门禁所在的相位**——门禁不只是"阈值宽松"，而是**不可达**；配置注释所称的 0.36 亦与实测（仅单元测试口径 `0.5093`）不符。

这一缺失有直接代价：最近的提交全部是补救性的，且集中在同一处缺陷模式上——连续两次修复"配额达成率的 SQL（表名/列名/单位）"，而**表名写错正是集成测试存在的唯一理由**。有 60 个集成测试专为捕获此类错误而写，却从未运行。列为 P0：没有它，项目是否健康无法回答。

**独立测试**: 执行完整构建校验后，集成测试报告目录出现且含集成测试报告；覆盖率报告的数值包含集成测试所覆盖的代码。

**验收场景**:

1. **Given** 集成测试套件已编写并编译，**When** 执行完整构建校验，**Then** 集成测试被实际执行并生成报告目录（当前该目录不存在，报告数为 0）。
2. **Given** 覆盖率报告当前在集成测试执行**之前**的构建阶段生成，**When** 调整报告生成时机至集成测试之后，**Then** 报告中包含集成测试所覆盖的代码。
3. **Given** 测试用内存库的结构镜像滞后于生产迁移七个版本（缺用户邮箱列、商机金额列，以及销售配额、定时导出、数据保留三组表，权限种子停留在早期版本），**When** 补齐镜像，**Then** 因**结构缺失**（表不存在/列不存在）导致的集成测试失败数为 0。
4. **Given** 覆盖率门禁阈值显著低于实际覆盖率（配置为 `0.30`，而实测仅单元测试口径已达 `0.5093`；注释自述"预留余量"并称现状为 0.36，该数字实测不成立），**When** 上调至实测值附近，**Then** 覆盖率回退时构建失败。
5. **Given** 新增一项生产迁移但未同步测试库镜像，**When** 执行完整构建校验，**Then** 守卫检查失败并指出缺失的表或列（这是防止本次修复随后续版本再次失效的唯一手段）。
6. **Given** 存在一个命名不合集成测试约定、会被单元测试范围捕获的集成测试类，**When** 重命名归入集成测试范围，**Then** 其既有覆盖不丢失。

### 用户故事 2 - 前端三道门禁真正生效（优先级：P0）

前端代码的 Lint、覆盖率、端到端测试必须成为会失败的关卡，而不只是配置项。

**优先级理由**: 三个门禁全部处于"配了但不管"的状态。Lint 已是持续集成的步骤，但当前**执行失败**（31 个错误、9 个警告），意味着流水线要么是红的、要么根本没在跑；覆盖率配置只有采集器和报告器、**没有任何阈值**，可无限退化而不报警；端到端测试有 3 个用例、有运行脚本，但**从未进入持续集成**。与用户故事 1 同因——门禁的名义存在掩盖了实际失效。

**独立测试**: Lint 命令输出零问题；覆盖率命令在覆盖率低于阈值时以失败退出；持续集成流水线包含端到端测试步骤。

**验收场景**:

1. **Given** Lint 当前有 31 个错误与 9 个警告，**When** 修复后执行 Lint，**Then** 输出 0 error 0 warning。
2. **Given** 覆盖率配置无阈值，**When** 添加阈值后执行覆盖率测试，**Then** 覆盖率低于阈值时命令以非零码退出。
3. **Given** 持续集成未运行端到端测试，**When** 加入该步骤后触发流水线，**Then** 端到端测试步骤被执行且结果影响流水线状态。

### 用户故事 3 - 关闭已确认的 5 项鉴权缺陷（优先级：P1）

安全负责人要求所有信任边界的授权都在服务端强制执行，且不依赖任何绕过机制。

**优先级理由**: 章程原则三明确"授权必须在服务端强制执行，仅隐藏 UI 元素绝不构成访问控制"，且为**不可协商**。已逐条确认 5 处违背：

1. **密钥认证注入管理员身份**——代码显式构造管理员语义的主体，注释自述"绕过行级权限"。由于行级权限的"无限制"判定与权限切面都以管理员角色短路放行，该主体获得了**全量数据访问权**，与密钥自身被授予的范围无关。
2. **实时通道绕过用户失效机制**——握手仅从令牌解析用户标识，**不校验用户启用状态与令牌版本**，因此被停用用户的旧令牌仍可建立连接；同时允许任意来源，令牌经由查询串传递。
3. **出站地址无服务端请求伪造防护**——通知通道仅检查协议前缀；Webhook 回调地址**完全无校验**。两者都不阻止指向回环地址、私有网段、链路本地地址或云元数据端点的地址。
4. **三个控制器无操作级权限校验**——其中两个为高敏感：个人数据导出（合规/GDPR 语义）与数据保留策略（破坏性操作），另有定时导出。
5. **定时导出的读取端点存在越权读取**——列表接口接受任意用户标识参数，且列表、详情、执行记录三处均无归属校验，任何已认证用户都能读取他人订阅。

> 注：经复核，绝大多数控制器**已有**操作级权限注解；未加注解者多为公开或自助端点（登录、公开门户、表单提交、邮件追踪、退订），**不应改动**。全局搜索虽无注解，但其数据范围已在服务层按当前用户过滤，且系统中**不存在**对应权限码——加注解会使搜索功能对所有用户失效，故**明确不加**，此项作为显式决策记录。本项仅修复上述真实缺口，**不涉及**"RBAC 形同虚设"式的全面整改。

**独立测试**: 三项手工验证全部被拒——受限密钥读取授权范围外数据、已停用用户的旧令牌建立实时连接、创建指向私有网段的回调地址。

**验收场景**:

1. **Given** 密钥认证当前注入管理员身份从而获得全量数据访问，**When** 改为按密钥所属主体的实际角色与权限授权，**Then** 范围受限的密钥无法读取超出授权的数据（原先返回全量）。
2. **Given** 实时通道握手不校验用户启用状态与令牌版本，**When** 补上校验，**Then** 已停用用户的旧令牌握手被拒绝。
3. **Given** 出站地址校验仅检查协议前缀、回调地址完全无校验，**When** 统一实施服务端请求伪造防护，**Then** 指向回环地址、私有网段、链路本地地址、云元数据端点的地址被拒绝，且**重定向后**的目标地址同样被校验。
4. **Given** 合规导出、数据保留策略、定时导出三个控制器无操作级权限注解，**When** 补上**既有**权限码，**Then** 无对应权限的用户调用返回 403，有权限的用户正常返回。
5. **Given** 全局搜索没有权限注解且系统中不存在对应权限码，**When** 复核其数据范围，**Then** 确认搜索已在服务层按当前用户过滤、保持不加注解，且该判断被记录为显式决策而非默认省略。
6. **Given** 用户甲已登录，**When** 以用户乙的标识调用定时导出的列表、详情或执行记录，**Then** 不得返回乙的订阅数据。

### 用户故事 4 - 14 个页面恢复加载，部署可一键启动（优先级：P1）

用户访问配额、数据保留、定时导出三个模块的页面时必须看到真实数据；维护者从干净检出执行容器编排时必须能启动可用系统。

**优先级理由**: 这三个模块共 14 个页面**全部无法加载数据**，根因是凭据失配（详见边界情况），且请求失败被前端吞入空状态，表现为"空表"而非报错——这很可能是最近一次"配额列表页空表修复"未能根治的真实原因。同时容器编排有三处缺陷使干净检出无法启动或与迁移机制冲突。两者都是**阻断性**的：功能存在但用户无法使用。

**独立测试**: 登录后逐个访问 14 个页面全部加载出数据；从干净检出执行容器编排，首页返回非空白内容。

**验收场景**:

1. **Given** 三个模块的 API 客户端读取了全站并不存在的凭据存储键，**When** 改为读取全站统一键，**Then** 13 个页面正常加载数据（配额 6 + 数据保留 4 + 定时导出 3，即三个客户端各自的全部消费方；第 14 个页面即合规导出页属另一根因，见 SC-G04）。
2. **Given** 合规导出页面使用独立 HTTP 客户端且完全未携带凭据，**When** 收口到全站统一客户端，**Then** 该页面正常加载（合计 14 个页面全部恢复）。
3. **Given** 配额列表当前显示空表，**When** 修复凭据后访问，**Then** 列表显示数据（据此确认与最近那次"空表修复"的因果关系）。
4. **Given** 凭据缺失时请求失败不触发重新登录、且错误格式与全站不一致，**When** 统一走既有客户端，**Then** 401 触发登出跳转、错误信封与全站一致。
5. **Given** 干净检出且未构建前端产物，**When** 执行容器编排，**Then** 首页返回非空白内容。
6. **Given** 容器编排将版本化迁移目录挂载为数据库初始化脚本目录，**When** 移除该挂载，**Then** 数据库结构仅由版本化迁移管理，无两套机制竞争。
7. **Given** 容器编排的跨域允许来源指向开发端口而前端实际服务在另一端口，**When** 修正为实际端口，**Then** 分离部署下跨域请求成功。

### 用户故事 5 - 消除已定位的性能与一致性损耗（优先级：P2）

维护者要求移除已知的无效开销与数据一致性风险，遵守章程原则五"禁止 N+1 查询模式"。

**优先级理由**: 六处已逐条定位。它们不阻断功能，但每一处都在热路径上，且有明确的低风险修法。其中"操作人未自动填充"是**审计与合规导出的地基**——当前依赖业务代码手写，存在系统性遗漏，影响范围超过性能本身。列为 P2：有收益但无阻断性，风险最低，可最后实施。

**独立测试**: 单次请求不再产生重复的产品查询；授权校验命中缓存；操作人字段在新增实体时自动写入。

**验收场景**:

1. **Given** 日志过滤器包装并复制每个响应的完整响应体，而其日志只使用状态码与耗时、**从不读取响应体**，**When** 移除包装，**Then** 日志内容不变且不再为每个请求缓存响应体。
2. **Given** 角色权限查询在每次授权校验时执行两次数据库查询且无缓存，**When** 引入缓存，**Then** 同一角色的后续校验不再查库；且角色或权限变更后缓存被失效。
3. **Given** 报价单的金额计算与明细构建对同一批产品各查询一次（合计两次查询），**When** 合并为一次查询，**Then** 查询次数降为该批产品一次。
4. **Given** 密钥认证的状态写回未声明事务且计数采用读-改-写，**When** 事务化并改为原子更新，**Then** 并发认证下计数不丢失。
5. **Given** 实体新增/更新仅自动填充时间戳、操作人依赖业务代码手写，**When** 操作人一并自动填充，**Then** 新增实体自动记录操作人。
6. **Given** 数据权限可见范围每次查询整张用户表且无缓存，**When** 引入缓存，**Then** 后续查询命中缓存；且用户或部门变更后缓存被失效。

### 边界情况

- **补齐测试库镜像后集成测试仍可能失败，且原因必须四分**：①镜像缺失；②内存库与生产库的方言与默认值差异（自动更新时间戳语义、复杂类型列、时间精度、唯一约束中的空值语义、字符集大小写敏感性）；③**测试假设已过期**（权限矩阵在本规格要镜像的那次迁移中被扩充，基于旧矩阵的断言会失效）；④**真实代码缺陷被首次暴露**。①②是本次要清零的目标；③要修断言但**不得放宽到失去意义**；④**不得在本规格内顺手修复**，应登记转入后续规格——否则本规格会变成一个开放式的缺陷容器。
- **本规格可能以"构建仍为红"收尾**：本次范围裁决只承诺清零环境类失败（见 Clarifications）。若业务逻辑类失败未清零，门禁会被真实接线但持续集成为红。**绝不允许**为了让灯变绿的替代做法：把阈值留在低位、放宽断言、或删除失败用例——那正是本规格要修的病。
- **密钥去管理员化会连带两处语义**：行级权限的"无限制"判定与权限切面的管理员短路放行都会被触发。改造必须把该判定改为**显式三分支**（管理员放行 / 无主体放行 / 其余走行级判定），**必须保留"无主体"分支**——它服务于系统内部调用（定时任务等），删掉会导致大面积失败。开放端点的跨行级可见性因此变为一个**必须显式决定并记录**的语义，不能靠推断。
- **密钥去管理员化会改变既有授权结果**：原先能读全量的调用方将收到 403 或空结果。这是安全修复的**预期效果**，不是回归，不得据此回滚。
- **权限缓存必须在角色-权限变更后失效**，否则授权变更不生效，形成"改了权限但没改行为"的静默故障。
- **数据权限可见范围缓存必须在用户与部门变更后失效**，否则组织调整后可见范围滞后。
- **缓存必须使用进程内实现，不得使用已有的外部缓存服务**：集成测试把缓存客户端替换为测试替身，若用外部缓存，缓存行为在测试中将**静默不被验证**，等于给本规格自己制造一个新的"名义存在而实际失效"机制。
- **进程内缓存与集成测试共享同一个应用上下文**：若写操作不失效缓存，测试会变成顺序相关（前一个测试创建的角色被后一个测试读到）。测试基类必须清理缓存。
- **操作人自动填充只对新增生效**，历史数据不追溯；清理业务代码中重复手写的赋值必须逐处核对后再删。
- **实时通道允许的来源复用既有的跨域配置**：若该配置在部署环境中配错，会导致前端通知连不上；令牌经查询串传递有被日志记录的风险。
- **出站地址防护若不覆盖重定向**，攻击者可用重定向绕过首跳校验；白名单若默认放行私网则等于没有防护。
- **覆盖率阈值上调幅度需以实测值为准**，过高会导致正常开发频繁失败，过低则门禁无效。若实测值明显偏低，应当补测试，或按实测值设定**并在数据模型中记录实际数字与理由**，不得虚设。
- **测试库镜像是机械转译，不是语义重写**：生产迁移含大量特定于该数据库的语法，必须转译为目标内存库的既有形制，不得整段粘贴；且新增列必须落在对应的建表语句内，不得在文件末尾追加变更语句。
- **新增角色授权语句依赖角色种子已存在**：镜像顺序必须保持在角色种子之后，否则会静默插入 0 行，使角色相关测试以"无权限"**假绿**。
- **构建流水线前端步骤可能不是 Lint 先失败**：持续集成使用的运行时版本低于本地包的版本要求，首个失败步骤可能更早（依赖安装阶段）。实施前必须定位真正的首个失败步骤，否则会误判修复对象。
- 本 spec **不改数据库结构、无新增迁移**；测试库镜像的补齐属于测试资产，不属于生产迁移。

### 实施期实测结果与范围裁决（T017/T018，2026-09-12）

**先说结论**：①"镜像缺失"与②"方言差异"两类环境类失败**已清零**；连接入 failsafe 这一动作本身都没有失败（`0E`：无上下文加载失败、无 SQL 异常）。但剩余 6 例集成测试与 3 例单元测试需要**产品语义决策**，按边界情况④「不得在本规格内顺手修复，应登记转入后续规格」**收缩出本规格**。此收缩为 T018 明文授权，记录于此，不构成静默降低标准。

**为什么是收缩而不是修**：这 9 例的根因分散在 4 个互不相干的机制上，且每一条都要先决定"是对的还是错的"，而那个决定属于产品而非工程收口——本规格无权替它决定：

| 被收缩项 | 需要先做的产品决策 |
|---|---|
| `SystemEnhancementIT` ×2 | `export_job.export_format` **无任何迁移创建**（实体声明了字段，V40 建表没有这一列）——是补一条迁移，还是删掉实体字段？**生产库同样缺列，导出功能在生产即为 500**，是阻断性缺陷 |
| `UserIT` ×2 | 登录用 `updateById(user)` 递增 `@Version`，客户端不可见的副作用污染了乐观锁令牌——是改为定向 SQL 更新（不动版本号），还是接受"登录即令他人在编辑中的表单失效"？ |
| `OpportunityIT` | `CloseRequest.closeResult` 的 `@NotBlank` 使 Bean Validation 的 400 先于域错误 422——两层校验谁优先，是契约决定 |
| `IntegrationHubIT` | `WebhookDeliverer` 退避 1s/5s/30s 使投递记录 ~36s 后才落库，用例等 1.5s——退避参数是否要可配置（可配置就不只是测试问题，而是生产可观测性问题）？ |

**已在本规格内修复的 5 例**（边界情况③"要修断言但不得放宽到失去意义"）：`RoleIT.adminCreatesRole`（环境类，角色码撞 V75 预置）、`RoleIT.meReturnsMenusAndPermissions`、`CustomReportsIT.stageReport`、`FieldVisitIT.visitLifecycle`、`CustomerIT.customerLifecycle`（后 4 例为测试腐化）。其中两处修复手法值得留档：**菜单数与权限数不再写死**，改为与字典接口做集合相等断言（检验"ADMIN 兜底分支取到全量"，而非"目录恰好是 N 项"）；**时间窗不再写死日期**，改为按当天计算——这两类断言原本不报错、只静默失败，是最难归因的一种腐化。

**SC-G01 的最终口径**：集成测试**确实执行**（**66 份报告** ≥ 60，对应 66 个 `*IT` 类；T062 复核时由先前快照的 64 份更新为实测值）且**环境类失败为 0**；构建以 6 例业务类失败告终，`mvn -B verify` 退出码非 0。这正是 SC-G01 已声明的**已知后果**，不是缺陷。

## 需求（必填）

### 功能需求

#### 集成测试执行与覆盖率

- **FR-G01**: 构建必须在集成测试与验证相位执行集成测试类（`**/*IT.java`），当前无任何执行声明。
- **FR-G02**: 覆盖率报告必须在集成测试执行**之后**生成，确保数值包含集成测试所覆盖的代码（当前报告绑定在集成测试之前的相位）。
- **FR-G03**: 覆盖率门禁阈值必须上调至实测覆盖率附近，不得保留显著低于实测值的"预留余量"，并移除为该余量背书的免责注释。**实测基线（2026-09-12，见 [baseline.md](./baseline.md)）**：阈值配置为 `0.30`，而仅单元测试口径的实际覆盖率已达 **0.5093**，余量约 **21 个百分点**——远超配置注释自述的 6 个百分点，且注释所称"覆盖 0.36"与实测不符，说明该数字从未被核对。

#### 测试库结构一致性

- **FR-G04**: 测试用内存库的结构必须与生产迁移保持一致，补齐自 V70 起未镜像的七项迁移，含用户邮箱列、商机金额列，以及销售配额、定时导出、数据保留三组表。
- **FR-G05**: 测试库的权限种子数据必须与生产一致，镜像 10 个预置角色及其授权（当前停留在早期版本）。该迁移是**纯增量**的——它只新增角色与授权，不修改既有的管理员/销售/客服角色，镜像时不应改写既有种子。
- **FR-G06**: 命名不符合集成测试约定的集成测试类必须重命名归入集成测试执行范围（当前存在一个以 `*ITTest` 命名的集成测试类，会被单元测试执行范围捕获而非集成测试范围），且不得丢失其既有覆盖。
- **FR-G07**: 必须存在一项自动化守卫，在新增生产迁移而未同步测试库镜像时使构建失败。**这是防止本规格修复随后续版本再次失效的唯一手段**——本次缺陷的本质正是"机制建了但未回填"，若只补数据不加守卫，下一个迁移会立刻重演。

#### 前端门禁

- **FR-G08**: 前端 Lint 必须达到 0 错误 0 警告。
- **FR-G09**: 前端覆盖率必须配置阈值门禁，低于阈值时命令以非零码退出。
- **FR-G10**: 持续集成流水线必须执行端到端测试。

#### 鉴权

- **FR-G11**: 密钥认证必须按密钥所属主体的实际角色与权限授权，不得注入管理员身份或任何可满足"数据权限无限制"判定的主体。改造必须把该判定改为显式三分支（管理员放行 / 无主体放行 / 其余走行级判定），**必须保留"无主体"分支**——它服务于系统内部调用。
- **FR-G12**: 实时通道握手必须校验用户启用状态与令牌版本，与 HTTP 认证路径保持一致；且允许的来源必须**复用后端已有的跨域允许来源配置**，不得为通配，也不得新增第二个来源配置项。
- **FR-G13**: 所有出站 URL（通知通道、回调地址）必须统一实施服务端请求伪造防护，拒绝回环地址、私有网段、链路本地地址与云元数据端点，并覆盖重定向跳转；同时提供**环境变量白名单**作为合法内网集成的显式出口，默认配置下不放行任何私网地址。
- **FR-G14**: 合规导出、数据保留策略、定时导出三个控制器必须声明**既有**的操作级权限码，不得为此次修复新增任何权限码。
- **FR-G15**: 全局搜索控制器**不得**添加权限注解——其数据范围已在服务层按当前用户过滤，且系统中不存在对应的权限码；擅自添加会使搜索功能对所有用户失效。此判断必须作为**显式决策**记录在规格中，不由实施者临场判断。
- **FR-G16**: 定时导出的读取端点必须按当前登录用户限定范围，不得接受任意用户标识参数读取他人订阅（当前列表接口接受任意用户标识，且列表、详情、执行记录三处均无归属校验）。

#### 前端凭据一致性

- **FR-G17**: 配额、数据保留、定时导出三组 API 客户端必须使用全站统一的凭据存储键，并统一走既有 API 客户端（当前为三份重复的独立实现，绕过了既有客户端）。改造必须**保持各方法的既有签名与返回结构**，使调用页面无需改动——注意这三个模块的后端返回的是**裸响应体而非全站错误信封**，客户端不得按信封解包。
- **FR-G18**: 合规导出页面必须使用既有 API 客户端，不得使用未配置凭据的独立 HTTP 调用。

#### 部署编排

- **FR-G19**: 容器编排不得将版本化迁移目录挂载为数据库初始化脚本目录（该机制按文件名字母序执行，与版本化迁移冲突）。
- **FR-G20**: 容器编排的前端服务必须使用能产出构建物的镜像，使得干净检出即可启动，无需预先手工构建。
- **FR-G21**: 容器编排的跨域允许来源必须与前端实际服务端口一致。

#### 性能与一致性

- **FR-G22**: HTTP 日志过滤器不得缓存响应体——其日志只使用状态码与耗时，从不读取响应体。
- **FR-G23**: 角色权限查询必须缓存，并在角色或权限变更后失效（当前每次授权校验触发两次数据库查询）。
- **FR-G24**: 报价单的金额计算与明细构建必须共享同一次产品查询（当前同一批产品被查询两次，形成 2N 次查询）。
- **FR-G25**: 密钥认证的**使用记录**写回必须**不丢失计数**（禁用读-改-写），且**不得触碰授权列**（`status` 等）——否则在途鉴权能覆盖并发撤销的结果。（**措辞经 T062 修正**：原文为"状态写回必须事务化"，把"事务"这一手段当成了要求。实施采用**单条原子更新语句**（`use_count = use_count + 1` 交给数据库自增 + 只写 `last_used_at`），**故意不加 `@Transactional`**：单语句无中间态、无可回滚之物，而事务会延长鉴权热路径的连接与行锁持有时长。理由与取舍见 Clarifications 的「实施期修正」。）
- **FR-G26**: 实体**新增**必须自动填充操作人（当前仅填充时间戳，操作人依赖业务代码手写，存在系统性遗漏）。（**范围经 T062 收窄**：原文含"更新"路径。实施只覆盖新增——**全部实体与全部迁移中都不存在 `updated_by` 列**，更新路径在本规格内不可实现；新增该列须先做产品决策且本规格明确不改 schema，故移出并转交后续规格。）
- **FR-G27**: 数据权限可见范围查询必须缓存，并在用户或部门变更后失效（当前每次查询整张用户表）。

### 关键实体（涉及数据）

- **无新增数据库表，无新增迁移**。本 spec 不改变生产数据结构；用户故事 1 中的测试库镜像属测试资产。
- **缓存条目（新增，进程内）**：角色权限集合缓存（按角色标识）、数据权限可见范围缓存（按用户标识；其值的正确性取决于**部门成员集合**，故用户或部门的任何变更须触发**全量失效**——按用户单键缓存、按部门维度失效，漏失效即越权读数据）。二者均须明确存活时间（**不超过 60 秒**）与失效时机，并在相关写操作后主动失效。**必须为进程内实现**——集成测试把外部缓存客户端替换为测试替身，若用外部缓存，缓存行为将在测试中静默不被验证，等于给本规格自己制造一个新的"名义存在而实际失效"机制。
- **配置项**：出站地址防护的拒绝范围与**环境变量白名单**（默认不放行任何私网地址）、实时通道允许来源（**复用既有的跨域允许来源配置，不新增第二个来源配置项**，避免两处配置各自漂移）、前端与后端各自的覆盖率阈值。

## 假设

- 集成测试设计上自包含：使用内存数据库并将 Redis 替换为测试替身，**不需要**真实数据库或缓存服务，因此可在持续集成中直接运行。
- 上述全部缺陷均已在代码与工程配置中**逐条确认**（含具体文件与行号），非推测结论。
- 集成测试数量以编译产物中实际存在的集成测试类为准（不少于 60 个）。
- **测试库与生产库的差异仅限未镜像的那七项迁移**——此为待验证前提，必须逐表核对确认；若不成立（即更早的迁移也未对齐），镜像范围相应扩大。
- 持续集成的运行时版本需与前端包管理器声明的最低版本要求对齐；实际首个失败步骤在实施前定位，不预设为 Lint。
- **本规格可能以"构建仍为红"收尾**：本次范围裁决只承诺清零环境类失败；若业务逻辑类失败未清零，门禁将被真实接线但持续集成为红（见 SC-G01 的已知后果）。
- **数据保留的归档缺陷**（归档未真正生效、无事务边界、无行数上限）**不在本 spec 范围**——其工作量与风险不同量级，另立独立规格。
- **行级数据权限向合同、报价、订单、发票、工单的回填**不在本 spec 范围。
- **双因素认证**（已有完整规格但尚未实施）不在本 spec 范围，其实现另行推进。
- 国际化补全、通用增删改查组件抽象、前端数据请求库落地、预加载清单重构、多租户决策均不在本 spec 范围。
