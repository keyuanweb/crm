# 研究：登录验证码技术选型与决策

## R1 验证码图片生成方案

**决策**: 使用 JDK 内置 `java.awt`（BufferedImage + Graphics2D）生成图形验证码，输出 PNG 字节流，前端以 base64 data URL 内联展示。

**理由**:
- YAGNI（章程原则五）：不引入第三方验证码库（如 EasyCaptcha、Hutool、kaptcha），仅需简单字符干扰图。
- `java.awt` 在 JDK 17 可用，无额外依赖；服务端生成图片避免前端纯客户端生成（可被脚本逆向）。
- 4~6 位字母数字 + 干扰线，满足基本防自动化要求（本系统为内网/演示场景，无需滑块/点选等高强度验证码）。

**备选方案（拒绝）**: 引入 EasyCaptcha / kaptcha —— 增加依赖且功能过剩；前端纯 Canvas 生成 —— 答案会暴露在客户端，无安全价值。

## R2 验证码会话存储与一次性语义

**决策**: 答案存 Redis，key `auth:captcha:<captchaId>`，value 为大写答案字符串，TTL 300 秒；校验时 `GET` + `DEL` 原子地消费（先取后删），实现一次性。

**理由**:
- 复用现有 RedisTemplate（已有 `auth:fail:`、`auth:refresh:` 前缀惯例）。
- Redis `get`+`delete` 两步在单实例下足够；无需 Lua 原子脚本（并发登录场景极低，YAGNI）。
- TTL 自动清理过期验证码，无需额外定时任务。

## R3 验证码校验时机与失败计数隔离

**决策**: 在 `AuthService.login` 入口先校验验证码（独立于凭证），验证码错误直接抛业务异常，**不**调用 `recordFailure`。

**理由**:
- 章程原则三（安全）：验证码作为前置人机校验，先于凭证。
- FR-007 要求验证码错误不累计登录失败次数——避免攻击者通过刷错误验证码触发合法用户的账号锁定。

## R4 前端验证码刷新交互

**决策**: 登录页新增验证码输入框 + 图片（点击刷新）。图片 src 用接口返回的 data URL；点击图片或登录失败后重新调用 `GET /auth/captcha` 并清空输入框。

**理由**: data URL 无需处理 cookie 或额外图片请求的会话关联；刷新即重新拉取，旧 captchaId 自然被新请求覆盖。

## R5 错误码设计

**决策**: 新增 `CAPTCHA_INVALID(422)` 与 `CAPTCHA_EXPIRED(422)` 两个错误码，与现有 422 校验类错误码风格一致。

**理由**: 区分"输入错误"与"过期/不存在"两类失败，前端可给出差异化提示（FR-002/FR-003/FR-005）。
