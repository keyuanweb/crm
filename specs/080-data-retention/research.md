# Research: 数据保留策略（Data Retention Policy）

**创建日期**: 2026-08-27

## 决策记录

### 决策 1: 归档表创建方式

**选择**: 通过 Flyway 迁移脚本动态创建归档表（实体 + _archive 后缀）。

**理由**:
- 归档表需要与主表结构一致，动态创建保证结构同步
- Flyway 迁移脚本可在策略创建时执行（或通过预定义脚本）
- 避免手动维护归档表结构

**替代方案**:
- 统一归档表（所有实体归档到同一表）：结构不匹配，不推荐
- 应用层动态创建表：绕过 Flyway，不推荐

### 决策 2: 归档操作执行方式

**选择**: 分批归档（每批 1000 条），避免锁表。

**理由**:
- 大批量归档会导致锁表，影响在线业务
- 分批归档降低锁表时间（每批 ≤ 5 秒）
- 通过执行日志记录每批处理数量

**替代方案**:
- 一次性归档：锁表时间长，影响业务
- 实时归档（数据创建时判断）：增加写入延迟

### 决策 3: 合规导出执行方式

**选择**: 同步导出（≤10 万行）+ 异步导出（>10 万行）。

**理由**:
- 小数据量同步导出响应快，用户体验好
- 大数据量异步导出避免超时
- 复用 016 导出中心的导出逻辑

**替代方案**:
- 全部异步导出：用户体验差（需要等待）
- 全部同步导出：大数据量超时

### 决策 4: 数据保留期限计算

**选择**: 基于实体创建日期（created_at）计算保留期限。

**理由**:
- 创建日期代表数据产生时间，符合合规要求
- 与现有实体字段一致，无需额外字段
- 简单直观，易于理解

**替代方案**:
- 基于最后修改日期：数据可能更新，保留期限不确定
- 基于业务日期（如合同签署日期）：需要额外字段，复杂

### 决策 5: 归档数据恢复方式

**选择**: 管理员可通过恢复功能将归档数据移回主表。

**理由**:
- 归档可能是误操作，需要恢复能力
- 管理员权限控制，安全
- 恢复操作记录审计日志

**替代方案**:
- 不允许恢复：数据丢失风险
- 自动恢复：逻辑复杂，不推荐

## 技术调研

### 动态创建归档表

- 使用 Flyway 迁移脚本（V74__data_retention.sql）创建策略表
- 归档表通过应用层动态创建（实体 + _archive 后缀）
- 归档表结构与主表一致，额外添加归档时间字段（archived_at）

### Spring Schedule 复用

- 复用 079 模块的 Spring Schedule 配置
- 使用 `@Scheduled(cron = "0 0 2 * * ?")` 每天凌晨 2 点执行归档
- 通过 `@EnableScheduling` 启用调度

### 现有导出逻辑复用

- 复用 016 导出中心的 ExportService（筛选条件 → SQL 查询 → 文件生成）
- 复用 ExportController 的导出端点（通过 Service 层调用）

### 现有回收站逻辑复用

- 复用 025 回收站的软删除逻辑
- 归档操作类似软删除，但数据移到归档表而非回收站

### Flyway 迁移脚本

- 现有 schema 版本 73（079-scheduled-export 模块后）
- 新版本 74：创建 3 张新表（策略表/执行记录表/归档日志表）
- 迁移脚本命名：`V74__data_retention.sql`
