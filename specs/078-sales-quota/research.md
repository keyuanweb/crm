# Research: 销售配额分解（Sales Quota Decomposition）

**创建日期**: 2026-08-27

## 决策记录

### 决策 1: 配额分解数据结构

**选择**: 使用独立的 SalesQuota、SalesQuotaVersion、SalesQuotaBreakdown 三张表，而非在现有 SalesTarget 表上扩展。

**理由**:
- SalesTarget 是 020 模块的个人/全局月度目标，维度单一
- 配额分解需要层级关系（年度→季度→团队→个人），三表设计更清晰
- 版本管理需要独立表存储历史变更
- 避免在现有表上添加大量 nullable 列

**替代方案**:
- 在 SalesTarget 上扩展：增加 quarter/team/person 字段 → 复杂、冗余
- 使用 JSON 列存储分解关系 → 不可查询、不可关联

### 决策 2: 达成率计算方式

**选择**: 实时聚合计算（从 Opportunity 表聚合成交金额），而非预计算存储。

**理由**:
- 商机成交金额可能调整（合同变更），预计算需要额外同步逻辑
- 实时计算保证数据一致性
- 通过索引优化性能（Opportunity 表的 close_date + amount 索引）

**替代方案**:
- 预计算到 SalesQuotaAchievement 表 → 需要触发器或事件监听，增加复杂度
- 定时任务批量计算 → 数据可能延迟

### 决策 3: 配额调整的时间锁机制

**选择**: 已关闭期间（close_date < 当前日期且状态为 CLOSED）的配额不可调整。

**理由**:
- 已关闭期间的业绩已结算，调整配额会影响历史业绩统计
- 未关闭期间允许调整，但保留版本历史

**替代方案**:
- 完全禁止调整 → 业务灵活性不足
- 允许调整但影响历史数据 → 审计混乱

### 决策 4: 商机计入期间规则

**选择**: 按商机成交日期（close_date）计入对应期间。

**理由**:
- 成交日期代表实际业绩产生时间，符合财务核算原则
- 与现有 020 销售目标的统计逻辑一致

**替代方案**:
- 按商机创建日期 → 业绩归属期间不准确
- 按商机最后更新日期 → 多次更新导致业绩归属变化
