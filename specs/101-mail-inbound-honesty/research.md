## §2 为什么是「配置门」（三条路都比过）

| 方案 | 代价 | 结论 |
|---|---|---|
| 真接 IMAP | 凭证保管、增量拉取、失败重试，以及一个**产品决策**（哪封邮件算客户来信、落到哪个实体）——那是另一个规格，不是本项的收口 | 否（用户裁决） |
| 删掉端点/从清单移除 | 丢掉 062 交付的**演示能力**（`SC-E02` 与 062 的 US 都围绕它），且 `mail_sync:manage` 会变成指向空能力的死码 | 否（用户裁决） |
| **配置门** | 默认部署下那个按钮**必然报错**（用户体验的退步，已在 `spec.md` §6 如实声明） | **采纳** |

「配置门」的实质是把**「这个部署有没有收信源」这件事**从**沉默**变成**显式**：默认拒绝（不写任何东西），想演示就显式说「我知道这只是演示」。

## §3 状态码：409，否掉 501 与 503

实测 `ErrorCode` 的状态码分布：**400×10 / 401×8 / 403×8 / 404×38 / 409×30 / 422×48 / 429×2 / 500×3 / 503×1**。

- **501** 语义最贴（「服务端不支持该功能」），但**全仓零先例** ⇒ 客户端、八道门禁、以及任何按状态类分流的既有代码都没见过它。收益是语义纯度，成本落在整个生态。
- **503** 在本仓已被 `MFA_STORE_UNAVAILABLE(503, "认证状态存储不可用，请稍后重试")` 占为**「依赖暂时不可用、可重试」**。本情形**不可重试** ⇒ 复用会稀释那条口径。
- **409** 有 30 处先例，语义族正是**「服务端当前状态不允许该操作」**（`QUOTE_INVALID_STATE`、`CONTRACT_INVALID_STATE`、`ORDER_HAS_PAYMENTS`…）。日后真接上 IMAP 时，「账户未启用 / 凭证缺失」仍会落回 409 ⇒ **这个码在真实实现里也活着**，不是给「未实现」造的一次性占位。

## §4 零迁移：状态值域由实体常量维护

- `mail_sync_record.sync_status` 是 `VARCHAR(20)`：`V69__mail_sync.sql` 的行注释只是 `COMMENT 'SYNCED/FAILED'`，**无 CHECK 约束**；测试用 `schema-h2.sql` 同样无约束。⇒ 插入 `SIMULATED` **不需要 DDL**。
- **先例就是 030**：`V48` 里 `email_send_log.status` 与 `email_campaign.status` 的 COMMENT 至今只列旧值，而 `SKIPPED` 早就写进库了——**本仓既定做法是「迁移 COMMENT 不追、值域由实体常量维护」**（`EmailSendLog.STATUS_SENT`/`STATUS_SKIPPED`）。
- 因此本项**不新增迁移**，**前提是实测过**（读了 V69 与 H2 schema），不是「先假设不用 DDL 再取证」。

## §5 异常为什么继承 `BusinessException`（与发信侧刻意的差异）

发信侧的 `MailNotConfiguredException extends RuntimeException`：那处的**调用方**有权选择——营销群发降级为「记 `SKIPPED` 并继续」，事务性邮件则让请求失败。它是一个**可以被处理**的信号。

本处只有**一条**出路：回一个受控状态码与稳定 code。继承 `BusinessException` 意味着：

1. 它落进既有的 `handleBusiness`，拿到全仓统一的 `ApiResponse` 信封（不手写 JSON、不另开处理器）；
2. **多重保障**：即使日后有人漏改/删掉处理器，父类的处理器仍在（100 的 `RateLimitExceededException` 已是这个形），不会掉进 `Exception` catch-all 变成 500。

## §6 配置：默认值两处同向，且不给前端加探针

- **两处默认值必须同向（都是 `false`）**：`application.yml` 的 `${CRM_MAIL_INBOUND_DEMO_ENABLED:false}` 与 Java 侧 `@Value(...:false)`。本仓有过「代码默认 true、yml false ⇒ yml 胜出 ⇒ 代码默认值是死代码却会被读成真源」的陷阱（captcha），故此处的 yml 注释**明写「唯一真源是本行的 `false`，Java 侧只是缺失兜底」**。行形照 `crm.mail.host` 与 `captcha.enabled`。
  ⚠️ **由此产生一个判据后果**：IT 走 yml ⇒ 改 Java 侧的 `:false` 不会让任何 IT 变红 ⇒ **必须有一条直接构造该类的单测**钉住 Java 侧（见 `spec.md` 的 T8 与 `falsification-evidence.md` 的 D6）。
- **不给前端加「演示模式」探针**：没有端点暴露该开关，而为此新增端点会把本项从**收口**变成**开面**（新增一个对外可读的部署配置端点，还要处理它的权限）。⇒ 界面用**一条 Alert** 说清两种情形，前端**不需要知道**当前是哪种。代价是文案要同时覆盖两档（已写进 FR-017）。

## §7 前端必须扩成三向（不是「顺手美化」）

`MailSyncPage.tsx:207` 今天是：`row.syncStatus === 'SYNCED' ? 绿「已同步」: 红「失败」`。

⇒ 只把后端改成 `SIMULATED` 而不动前端，演示记录会被渲染成**红色「失败」**。那不是「没美化」，而是**同一个缺陷的第二次出现**（用另一个假象替换原来的假象）。故 FR-016 要求三向，且**未知值仍兜底为「失败」**——不把未知状态原样外泄给用户（`types/mail.ts` 的联合类型同时扩，让「只改后端」在编译期就被挡住）。

## §9 契约偏差的处置（为什么不能沿用 085 判例）

详见 `contracts/mail-inbound.md` §1 的对照表。一句话：085 是「契约对、实现错 ⇒ 改实现」；本项是「**契约写下了不实的行为** ⇒ 062 仍不动（冻结决策件），新行为写在 101 的契约里，差异逐条登记」。**不得**把本项写成「实现向契约靠拢」——方向是反的。

## §10 「零插入」的判据不能靠事务推理

默认路径上：方法带 `@Transactional`，异常在 `insert` 之前抛出 ⇒ 事务里确实**没有**插入语句。但**判据必须是正面断言**：

- 单测：`verify(mapper, never()).insert(any())`（直接钉住副作用，不依赖 Spring 的事务语义）；
- 集成：`GET /records` 的 `total == 0`（端到端可见的事实）。

理由：靠推理得出的结论会在重构后静默失效（比如有人把 `insert` 挪到判门之前、又在别处补一个回滚），而**没有任何断言会红**。故意设计破坏 **D3**（在抛异常前先 insert）来证明这两条断言真的看着副作用。

## §12 `apiClient.isVersionConflict` 的口径（登记，不改）

`frontend/src/services/apiClient.ts` 的 `isVersionConflict` **只按状态码 409 判定**（不读 `error.code`），其注释自称「409 = 乐观锁冲突」。本项的 409 **当前不会**被误读：实测邮件页只用 `extractErrorMessage`（`MailSyncPage.tsx` 两处），没有任何调用点接它。**本项不改** `apiClient`——为一个不存在的调用点改全局工具的语义，会把风险从「一处可查的口径」扩散到「所有 409 的判定」。此条登记在此，供日后者查。

## §13 覆盖缺口与假绿通道（**如实登记**）

1. **演示档的记录里 `fromAddress` 仍是硬编码的 `customer@example.com`**。它现在与 `SIMULATED` 状态和带演示标记的主题一起出现，被标注清楚了；但**它本身不是真实地址**，且**没有任何用例或门禁能判断一个 `fromAddress` 是否真实**（本项不去猜）。⇒ 登记为「演示数据的固有边界」，不假装解决。
2. **`demo-enabled=true` 只表示「允许生成演示记录」，不表示「收信源可用」**。键为 true 而 IMAP 完全不存在时，端点照样 200 并写出演示记录。这个口径写在 javadoc 与三处配置注释里；**不得**被读成连通性探测。
3. **默认拒绝会让默认部署下的按钮必然报错**——这是本项**有意**的代价（用户裁决），但它确实是一处行为变更，且**没有任何自动化判据能衡量「用户困惑」**。缓解只有 Alert 文案与三处配置注释。
4. **`SIMULATED` 记录不会被自动清理**。演示环境与生产若共用库，需人工清理——本项不新增该能力（新增它就要新增端点或定时任务，属于开面）。
5. **本项没有任何一条用例能证明「接上 IMAP 后同步是对的」**——因为没有实现。本项的证据只覆盖「默认拒绝」「演示标注」「界面渲染」三件事。
