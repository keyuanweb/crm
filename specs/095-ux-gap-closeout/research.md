## §1 高亮：提取既有实现，不新写

**决策**：把 `pages/search/SearchResultPage.tsx` 的页内私有 `Highlight({text, keyword})` 提取为 `components/ui/Highlight.tsx`，搜索页改从 barrel 引入。

**理由**：① 它是现成的、可参数化的、已经处理了**多词关键词**与**正则元字符转义**的实现，重写一遍只会得到一份更差的复制品；② 077 的教训在 `components/ui/index.ts` 的注释里写着——另起第二个平行 UI 目录会让「设计系统」退化成两套各覆盖一半的库；③ 门禁 R7 要求 `components/**` 下的组件必须**被引用**，走 barrel 出口即满足。

**替代方案**：在部门页里复制一份。**否决**：两份实现的转义行为一旦分叉，同一关键词在两个页面会高亮出不同结果。

**实测的两条约束**：
- 它的色值 `#ffe58f` **不在** R1 的 `BRAND_COLORS = ['#1677ff','#6366f1','#4f46e5','#4338ca','#eef2ff']` 里 ⇒ 搬到新文件**不触发 R1**。
- `SearchResultPage.tsx` **没有测试文件** ⇒ 提取不牵动既有用例；且从页面文件里 `export` 组件会踩 `react-refresh/only-export-components`（warn 档），提取本身就是避坑。

**承重的一条**：高亮用的关键词**必须与过滤用的是同一个值**（防抖后的 `q`）。否则会出现「节点被留下、却没标出命中在哪」——那是比不高亮更坏的形态（用户看不出为什么这个节点留下了）。

## §2 防抖：300ms、造新件、以及为什么必须同时改两处依赖

**决策**：新增 `hooks/useDebouncedValue.ts`（`useDebouncedValue<T>(value: T, delay = 300): T`），`DepartmentListPage` 的**过滤**与**自动展开 effect** 一并改挂防抖后的值。

**理由**：① 全仓**无任何防抖件**（`grep -rn debounce src/` 零命中；`hooks/` 七个文件里唯一的 `setTimeout` 是 `useNotificationSocket` 的重连退避，不是通用件）⇒ 这是本批**唯一需要造的新件**；② 阈值 300ms 是 `068` 的 T015 明文写的数，**不自行发明**；③ 两处依赖必须同时改——只改过滤会让「展开哪些节点」跟着**未防抖**的值走，出现「结果已稳定但展开态还在抽搐」。

**替代方案**：用 antd `Input` 的 `onChange` + `setTimeout` 就地写。**否决**：那是把同一段时序逻辑写进页面，且**无法单测**（页面级 fake timers 会与 `findBy*` 的等待互斥）。

**测试怎么写**：hook 自己的单测用 `vi.useFakeTimers()` + `renderHook`；**页面级**的防抖断言**不用** fake timers 跑整页（会与 antd 内部定时器缠死），改为断言**最终结果与不防抖时一致** + `findBy*` 等待。**如实说明**：「窗口内没有重算」这条**只在 hook 单测里量**，页面层只量最终一致性。

## §3 空状态：用 `PageState` 的 `empty`，但**不**用它的 `loading`

**决策**：树无数据时渲染 `<PageState state="empty" />`。

**理由**：① 它是 088 交付的三态原语，**当前生产调用点为 0** —— 本项是它的**第一个消费者**；② 它的空态默认复用**既有键** `common.message.no_data`（`Empty` 的描述位），⇒ **零新增 i18n 键**；③ 它自带 `data-testid="page-state-empty"`，断言有稳定锚点。

**替代方案一**：自己写 `<Empty />`。**否决**：重复既有原语。
**替代方案二**：用 `<PageState state="loading" />` 替换 `<Card loading>`。**否决（重要）**：`PageState.tsx` 的文件头**明文禁令**——列表类页面已有自己的 `Card` 骨架，两层占位会打架。本项的加载态**保持**由 `<Card loading={loading}>` 承担。

**已知的语义边界（如实记）**：默认文案「暂无数据」与同屏的搜索框并置时，「库里没有部门」与「搜不到」两种含义会含混。**本项不新增键去区分**（`068` 的 `spec.md` 里「空状态」零命中，属 plan 层增强条款；区分两种空态超出任务字面要求）。记为遗留。

## §4 展开态：判「自相矛盾」而非「刻意设计」的依据

**事实**（两条都在同一文件里，互相抵消）：

```ts
// load() 内：算出所有有子节点的 id，意图是「全部展开」
if (n.children && n.children.length > 0) { allKeys.push(n.id) }
…
setExpandedKeys(allKeys)

// 另一个 effect：依赖 [searchValue, treeData]
if (searchValue.trim()) { …setExpandedKeys(keys) } else { setExpandedKeys([]) }  // ← 无条件清空
```

`load()` 完成后 `treeData` 变化 ⇒ 该 effect 立刻以 `searchValue === ''` 走 `else` 分支 ⇒ **每次加载后展开态都被清空**，`allKeys` 白算。

**决策**：`else` 分支改为「恢复全部展开键」。

**为什么判「自相矛盾」而不是「刻意的默认收起」**：如果是刻意收起，`load()` 就没有理由花一趟遍历去收集 `allKeys` 并 `setExpandedKeys` —— **那段代码的唯一可能意图就是展开**。两处对同一状态给出相反的期望，其中一处必然是笔误；而 `else` 分支的**注释**（「自动展开匹配搜索的节点」）只声明了搜索时的行为，**没有**为「空关键词要收起」提供任何理由。

**⚠️ 这是本项唯一一处有意的可见行为变化**（首次加载、以及保存/删除触发 `load()` 之后，树由「恒收起」变为「展开全部」）。**如实披露，不声称无副作用**，并记为一笔新的视觉欠账（`spec.md` SC-095-006）。

**为什么这一批必须碰它**：T015 要求防抖，而该 effect 的依赖里就有 `searchValue` —— 换依赖时不可能绕开这段逻辑。**顺手改**与**绕开走**之间，绕开走等于把已知的自相矛盾留在原地。

## §5 详情：为什么 `DepartmentDetail` 必须是一个组件

**决策**：把现内联的九项字段搬进 `components/DepartmentDetail.tsx`（纯展示，props 只有 `department`），页面 import 它。

**理由**：`068` 的 **T035 明确要求 `components/DepartmentDetail.test.tsx`** —— 而该文件**没有被测对象**。T030 与 T035 是**硬依赖**，不是风格偏好。

**代价与边界**：本项**只**抽这一个。(b) 里的 T011（搜索框）与 T012（树节点）**不抽** —— 没有任何任务硬依赖它们。

**门禁的硬要求**：新组件**必须被产品文件引用**，否则 R7 判孤儿（`ui:check` 退出码非零）。页面 import 即满足。

## §6 断点二择：Modal 与 Drawer **都渲染**，以及测试怎么跑到桌面分支

**决策**：照抄仓内唯一范式（`pages/map/UsageMapPage.tsx`）：`const screens = Grid.useBreakpoint(); const isMobile = !screens.lg`，两个容器**都写在 JSX 里**，用 `open={detailOpen && isMobile}` / `open={detailOpen && !isMobile}` 二择。

**理由**：① 仓内**只有这一处**范式，照抄优于发明；② 「都渲染、用 `open` 二择」的形态让**两个分支在任何环境下都存在**，不依赖条件渲染的分支裁剪。

**测试的坑（本批最大的一个）**：`setup.ts` 把 `matchMedia` 恒桩成 `matches: false` ⇒ `useBreakpoint().lg` 恒假 ⇒ `isMobile` **恒真** ⇒ **桌面分支永远不会执行**。而「用例全绿但它声称的场景根本没跑过」是本仓反复踩过的形态（091 的窄屏分支曾在全站空白的同时全量测试全绿）。

**解法**：在该测试文件内**覆盖 `matchMedia`**（范式见 `pages/map/UsageMapPage.test.tsx`：`matches: query.includes('min-width')`），并**留注释说明「全局桩未改、只有本文件覆盖」**。**桌面与移动各一条独立断言**，桌面那条在**默认桩下必须失败**——这正是 FR-095-011 的定向破坏之一（把 `isMobile` 写死 `true`，桌面断言必须转红）。

## §7 删除风险提示：用**真实数字**，不用通用警告

**决策**：`Popconfirm` 的 `description` 用该节点自己的 `childCount` / `memberCount` 现算文案。

**理由**：后端**真会**拒绝有子部门或有成员的删除（`DepartmentService.delete` 对两种情形抛同一码 `DEPARTMENT_HAS_CHILDREN_OR_MEMBERS`）。既然节点数据里**已经有**这两个数，让用户看到「这个部门下有 3 个子部门、12 名成员，删除会被拒绝」比一句通用警告**信息量严格更大**，且不引入任何新的计算。

**措辞的准确性要求**：文案必须说「**有子部门或成员时删除会被拒绝**」，而**不是**「此操作不可恢复」之类的泛化风险 —— 后者在本系统里不成立（逻辑删除 + 回收站），写上去就是**新的名实不符**。

## §8 为什么 T033/T034 是「订正」而不是「实现」

**实测（三条，缺一不可）**：

1. **详情的数据是同步的**：`openDetail(row) → setDetailData(row)`，取的是列表里已加载的那一行的**同引用**，**没有网络往返** ⇒ 结构上不存在「加载中」与「失败」两个窗口。
2. **详情不缺字段**：`DepartmentResponse` 已含 `createdAt` / `createdBy`（已解析成用户名）/ `memberCount` / `childCount`，FR-007 要的 7 个字段全在树里 ⇒ 排除「因为详情要再取一次完整数据、所以要加载态」这个常见的合理动机。
3. **后端没有那个端点**：`DepartmentController` 只有 `GET /tree` / `POST` / `PUT /{id}` / `DELETE /{id}`；而 `068` 的 `plan.md` 明文「**无新增后端 API／复用现有接口**」。

⇒ 要按字面做，只能**新增 `GET /departments/{id}`**，让页面为一个**已经握在手里**的对象再往返一次，然后为这次往返补一个加载态。**这是制造假加载态**，与 `068` 的 T028（加前端 `console.log`）同性质：**加了才是退步**。

**替代方案**：用既有的 `fetchDepartmentTree()` 当详情的数据源（同样能造出加载/失败窗口，且不碰后端）。**否决**：为了显示已有数据而重取整棵树，是把「有加载态」本身当成了目的。

**处置**：`068/tasks.md` 就地订正为「**结构性不适用**」，原文留痕。

## §9 三处推翻既有登记的复核

登记表上的 ✅ 不等于做了；**登记表上的 ⚠️ 也不等于就是真的**。以下三处的原判均被本次实测推翻：

### 9.1 「`t` 被遮蔽」＝假阳性

原判（`DepartmentListPage.tsx` 的 086 注释）：`load()` 里 `const t = await fetchDepartmentTree()` 遮蔽了 i18n 的 `t`，导致 catch 分支对数组调用函数、抛 TypeError，**加载失败时用户看不到任何提示**。

**复核**：`const t` 声明在 `try` **块**内；`catch` 是**平级**的另一个块作用域，不是 `try` 的子作用域 ⇒ catch 里的 `t` 解析到组件顶层的 i18n `t`。**遮蔽根本不在 catch 的可见范围内**。已用 node 复现同形结构自证（`falsification-evidence.md` §A）。旁证：`no-shadow` 未在 `eslint.config.js` 启用，`tsc` 亦不对此报错 —— 既无运行时 TypeError，也无编译期告警。

### 9.2 「`walk` 未防 `children` 缺失」的触发条件不成立

原判（同一注释的后半句）：`walk(n.children, …)` 未防 `children` 为空，缺失时同样抛错。

**复核**：后端 `DepartmentResponse.children` 初始化为 `new ArrayList<>()`（**恒非 null**）；`application.yml` 是 `default-property-inclusion: non_null`，它省的是 **null**，**空数组仍会序列化** ⇒ `children` 恒为数组。前端类型也把它声明为**必填**。⇒ 在本后端上**触发不到**。

**处置（1+2）**：**只订正注释**，代码不动。若按原判去「修」，会改一个不存在的原因、而真正的问题（如果有）继续留着。**顺带如实记**：同文件 `renderTreeNode` 与 `walk` 处**已经**对 `children` 做了 `&&` 判断，与类型声明**不一致**；这是一个**类型与实现的风格分歧**，不构成本批的合规问题，**不修**。

### 9.3 `067` 的 T001（逐节点默认样式值）不是缺口

原判（`067/tasks.md` 的订正块把 T001 记为「**部分**」并列入真缺口清单第 2 条）：实现有类型字段、缺逐节点赋值。

**复核**：`FlowNode` 的 `shadow?` / `borderRadius?` / `hoverHighlight?` **只有声明处本身**，全仓**无任何节点赋值、无任何读取方**（口径 `grep -rE`，非 BRE —— 用 BRE 时 `shadow?` 的 `?` 是字面量，读数会偏小）。而 `spec.md` 的 FR-001 判据（节点有阴影/圆角/悬停）由页面级**统一默认样式**满足，**spec 全文没有逐节点要求**（逐节点只出现在 `plan.md`/`tasks.md` 的实现形态描述里）。

⇒ 逐节点补值会产生**没有消费者的字段值** —— 只填数据是「类型齐但无人读」，若同时让页面去读它，就把**统一默认值拆成了逐节点值**（那是另一项、另一套判据）。**088 刚清过真孤儿（`ContactsCard.tsx`）**，本仓对「无人引用的东西」有明确态度。**订正为非缺口，不补做。**

## §10 `FR-003` 的订正为什么必须覆盖三处，以及它与章程原则五的关系

**三处是同一事实的三个表述**，只改一处就会**重演 094 的错**（那次改了 SC-094-006 却漏了兄弟行，属我自己的实证教训）：

| 落点 | 原文 |
|---|---|
| `068/spec.md` 的 `FR-003` | 「系统**必须**支持**分页**显示部门列表（默认 20 条/页）」 |
| `068/spec.md` 的 **US1 验收场景 2** | 「**Given** 部门列表超过一页，**When** 管理员**切换页码**……」 |
| `068/research.md` §4 | 「决策：**前端分页**（树形节点展开后分页）」+「已知问题 1」自认「展开/收起状态难以保持」 |

**订正方向**：改为「部门树**全量展示、不分页**」，理由取 `spec.md` 自己的 Assumptions（「部门树全量加载（不采用懒加载），适用于 1000 个部门以内的场景」）与 `research.md` §4 自己写下的「已知问题 1」。

**与章程原则五「列表端点必须分页」的关系**（这一条必须写进订正块，否则订正看起来像在绕开章程）：该条针对的是**可分页的列表端点**（避免无界增长与 N+1 场景）。部门树走的是**树形全量端点** `GET /departments/tree`，单次返回整棵树，且规模被 Assumptions 钉在 1000 个部门以内。**⇒ 不属该条射程，订正不构成章程违规。**

**性质要写明**：这是**事后按现状订正**（照 090 的「事后立项回填」先例），**不是**「决策时就不做」。不写清楚这一点，就等于把一次「做了别的、没做这个」的偏差洗成一次有意的设计选择。
