## 背景：本规格的由来

本规格的起因是一批**无人认领的改动**：把项目的 Java 基线从 17 提到 25（两个 CI 作业 + 两个镜像 `FROM` + pom 三行）。那批改动已被退回原状，原文留档在 `parked-jdk25.diff`。

退回不是因为它写得不对，而是因为**实测发现"升到 25"不是一次配置调整**。在隔离副本中逐项量过：

| 阶段 | JDK 25 上的实测结果 | 根因 |
|---|---|---|
| 编译 | 200 个错误 / 5 个文件 | 本仓 pom **没有任何 `maven-compiler-plugin` 配置**，Lombok 一直靠 classpath 上的**隐式注解处理**；**JDK 23 起隐式注解处理被默认关闭**，Lombok 不运行，`@Getter/@Data/@Builder` 生成物全部消失 |
| 格式门禁 | `spotless:check` **0.97 秒即失败** | 固定的 google-java-format 1.19.2 在 JDK 25 上抛 `NoSuchMethodError`（`Log$DeferredDiagnosticHandler.getDiagnostics`）。是 `NoSuchMethodError` 而非 `IllegalAccessError`，故 `--add-exports` / `--add-opens` **修不了**。同一份代码在 JDK 17 上 `732 files clean` |
| 启动 | 应用**起不来** | JDK 25 产出 class major **69**；Spring Framework 6.1.1 内置的 ASM 只读到 **major 66（Java 22）**。逐字节改版本号实测：61–66 通过，67/68/69 全部抛 `Unsupported class file major version`；真实扫描探针报 `BeanDefinitionStoreException ... Unsupported class file major version 69`。**故"只改几处版本、不动框架线"在构造上就不可能** |
| 测试 | `Tests run: 540, Failures: 0, Errors: 482` | mockito 5.7.0 / byte-buddy 1.14.10 无法 mock JDK 25 的类（924 处）；JaCoCo 0.8.11 无法插桩（574 处） |

结论：**升到 25 = 跳框架大版本线**（Spring Boot 3.2.0 → 至少 3.5.x），并连带 springdoc、MyBatis-Plus、Flyway、Connector/J 等多条依赖线，是一个量级完全不同的独立工程。它的完整调研记录（含各组件的最低可用版本与已否决的替代路径）见 `jdk25-investigation.md`，供将来另立新项时直接取用——本规格**不浪费那次调查，本规格就是它的第一级台阶**。

而**升到 21 实测近乎零成本**。同一份源码、同一份 pom（结构一字未改，只把 `java.version` 从 17 改成 21），在隔离副本中：

- 编译：`565 source files with javac [debug release 21]` → BUILD SUCCESS
- 格式门禁：`732 files clean`
- 单元测试：`555 run / 0 failures / 0 errors`
- 完整验证：`mvn -B verify` **退出码 0**，555 单元 + 284 集成全绿，日志出现 `jacoco:0.8.11:check (coverage-check)` 与 `All coverage checks have been met.`，75 份 failsafe XML 报告
- **需要升级的组件数量：0**

原因是 class major 65 落在上述 ASM 实测天花板（66）之内——**同一个阻塞点，21 在门槛内、25 在门槛外**。21 也是 LTS，满足章程"后端：Java（LTS）"。

因此本规格的目标是 **17 → 21**，范围刻意收窄为"只动基线声明，不动任何依赖版本线"。25 另立新项。

- **若在新基线上出现失败用例**：本轮的隔离实测为 0 失败，但实施时若真的出现，处置按「澄清」Q2 的裁决执行——**让实现回到既有契约**，逐例留痕；不得改用例、放宽断言或标记跳过。

## 澄清 *（Clarifications）*

### Q1：升级目标定在哪个基线？

**裁决**：**JDK 21**（2026-09-13 裁决；本轮实测后由"JDK 25"改立）。

**理由**：25 实测要求跳框架大版本线（四个阻塞点见「背景」，均为"构建第一个中止的地方"），而 21 实测**零依赖升级**即可全绿。21 同样是 LTS，满足章程。分界点是一个可度量的事实：class major 65 落在框架内置 ASM 的读取上限（66）之内，25 的 69 在之外。

**代价**：本项不解决"长期停在旧框架线上"的问题——那需要单独立项。

**边界**：本项**不**包含任何依赖版本变更。实施中若发现"不升某依赖就上不去 21"，按 FR-J12 停止并报告。

**派生**：FR-J01–FR-J04、FR-J11–FR-J15；SC-J01、SC-J03–SC-J06；以及 `jdk25-investigation.md`。

### Q2：若新基线上出现失败用例，如何处置？

**裁决**：**让实现回到既有契约**（2026-09-13 裁决，沿用上一轮的决定）。

**理由**：本项目的既有契约不因运行时基线变化而变化。若某用例的失败确实源于**实现依赖了旧基线的行为**，那说明实现偏离了契约，修实现；改用例等于把契约降到实现的水位。

**代价**：可能需要逐例分析，比"改断言"慢。

**边界**：该裁决**只在"失败确实源于旧基线行为"时适用**。若失败源于用例本身写错、环境缺失或测试替身过时，那属于测试缺陷，按测试缺陷修——同样逐例留痕。**两种情形都不得以"删除/跳过/放宽"收场。**

**派生**：FR-J09、FR-J10。
