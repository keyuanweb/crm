# Feature Specification: 列表页与窄屏外壳几何的端到端护栏

**Feature Branch**: `092-geometry-e2e-guard`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "列表页与窄屏外壳几何的端到端护栏。把已经交付的 090（列表页内容区撑满）与 091（窄屏外壳塌陷）的几何判据变成能自动跑的机器门禁。"

---

## 背景：这条短板为什么必须补

090 与 091 两次交付，判据全是**量出来的**：

| 项 | 主判据的量 | 今天的守护手段 |
|---|---|---|
| 090 列表页撑满 | 卡片底边到内容盒底边的余量、幽灵滚动、分页位置 | **无自动化用例**——只有 `measure-fill-height.mjs`（人手动跑）+ 人眼截图 |
| 091 窄屏外壳 | 内容区可见宽、内容容器宽、菜单容器宽高 | **无几何用例**——单测只能断言**结构前提**（那条 `width: 0` 规则的命中类名是否存在），几何量不出来 |

原因不是懒：**测试环境（jsdom）没有布局引擎**，`clientWidth` / `getBoundingClientRect()` 全是假值，
几何在单测里**量不出来**。于是这两项修好之后，**任何一次外壳或 CSS 改动都能悄悄把几何改回去，
而全仓测试仍然全绿**——这正是 091 那个缺陷活了半年（从 `c8bc7f8`「016 移动端适配」起）的同一台机器。

本项补的就是这一步：**用能跑真实布局引擎的端到端用例把几何不变式钉住**，
接进已有的 `pnpm run test:e2e`（CI 已有 `e2e` 作业在跑它）。

### 本项的第一条设计约束：护栏必须先证明自己会红

本仓有过两次「看起来有门禁」的先例，本项**不得**成为第三次：

1. **091 的窄屏分支**：全站内容宽 0 的同时，全量测试**全绿**——
   因为断言全落在**文案**上（菜单拍平后文案完全正常），而坏掉的是**几何**。
2. **048 的 e2e 套件**：只填了用户名/密码，被前端验证码必填校验挡住、**请求根本没发出**，
   22/23 用例长期全红且**从未被执行过**。

所以本项的核心质量要求不是「新增多少条用例」，而是**两条反假绿判据**（见 SC-EG-005、SC-EG-006）：
判据必须**自带活性断言**（能把「跳过」变成「失败」），且必须留下**定向破坏留痕**（证明它会红）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 改坏列表页几何时，机器当场拦住 (Priority: P1)

开发者（或另一个 agent）调整共用 CSS / 外壳高度链条时，如果让列表页的卡片不再吃满内容区
（回到 090 之前「表格只按内容长、余量露成背景色」的形态），`pnpm run test:e2e` **当场变红**，
并且失败信息指出是**哪一页的哪一个余量**不对——而不是等到用户截图来投诉。

**Why this priority**: 090 修的是**用户直接看得见**的观感（表格下方那片空白，实测曾有 197–754px），
而它的判据**一条自动化用例都没有**。回归成本最低、用户感知最强，故排 P1。

**Independent Test**: 把 090 的修复改回缺陷写法（去掉 `frontend/src/index.css` 里
「列表页撑满」那段的某个入口），跑该用例确认**变红**；还原后复跑**转绿**。

**Acceptance Scenarios**:

1. **Given** 视口 1280×720 与一个**内容不足以撑满**的列表页（如 `/quotas`），
   **When** 打开该页，**Then** 页面根卡片的**底边**落在**内容盒底边**上——
   即 `滚动盒底边 − 滚动盒自身下内边距 − 卡片底边 − 卡片自身下外边距 == 0`（不写死绝对像素）；
   并且**不出现幽灵滚动**（滚动盒 `scrollHeight == clientHeight`）。
2. **Given** 同上，**When** 量同一页的余量，**Then** 卡片底边到**视口底边**的距离
   **恰好等于**其下方可见外壳的总高（页脚高 + 内容区下内边距 + 卡片自身下外边距）——
   即**除这笔可解释的外壳占位外，没有任何多余空白**。
3. **Given** 一个**内容超出**的列表页（如 `/customers`），**When** 打开该页，
   **Then** 用例**不得**断言「填满」——该页的契约是「按内容撑高、由滚动盒滚动」：
   滚动盒 `scrollHeight > clientHeight`，且**末行完整可见**（不被裁掉），
   卡片底边**不高于**上述那条「外壳占位」线（不能反而缩回去）。
4. **Given** 该用例跑完，**When** 读它的输出，**Then** 能看出**哪几页被判为「短页」、
   哪几页被判为「长页」**，以及每一页上它实际断言了哪条不变式。

### User Story 2 - 窄屏外壳的几何被钉住 (Priority: P2)

开发者调整断点或外壳结构时，如果让 ≤767px 的内容区再次塌陷（回到那条 **24px 的缝**），
或者让菜单条重新变成一个 **200×200 的方块**，端到端用例**当场变红**。

**Why this priority**: 091 的窄屏几何**今天没有任何东西守着**——单测只能断言
「使布局塌陷的那个类名在不在」（结构前提），**量不了宽度**。也就是说：
只要那个类名不被引入，内容区是 375 还是 24，单测**看不出来**。
窄屏下的 24px 缝 = 全站**不可用**，严重度与 P1 同级，但它已有一层结构断言的保护、
且 375 视口的用例比宽屏多一次登录与渲染，故成本略高、排 P2。

**Independent Test**: 把 091 的修复改回旧写法（窄屏照样渲染侧边栏组件）或直接破坏内容区宽度，
跑该用例确认**变红**；还原后复跑**转绿**。

**Acceptance Scenarios**:

1. **Given** 显式设定的 375×812 视口，**When** 打开任意采样页（`/stats`、`/customers`、`/orders`、`/roles`），
   **Then** **内容区可见宽度**（滚动盒的 `clientWidth`，**含其自身左右内边距**）
   等于**视口宽度**（允许的偏差只留给滚动条占位，见「口径边界」）；
   当前缺陷形态是恒 **24**。
2. **Given** 同上，**When** 量**内容容器宽度**（内容盒宽度），**Then** 它等于
   **内容区可见宽度 − 24**（＝视口宽 − 内容区自身左右内边距各 12），375 档即 **351**；
   当前缺陷形态是恒 **0**。
   > ⚠️ **这两个量必须分别断言、不得互相替代。** 只断言「内容容器宽 = 内容区可见宽 − 24」
   > 会被缺陷态**同时满足**（0 = 24 − 24）——那是一条会放过原缺陷的假判据。
3. **Given** 同上，**When** 量菜单容器，**Then** 宽度 **= 内容区可见宽度**（＝视口宽，**不是 351**），
   高度 = **其声明高度 48**；当前缺陷形态是 **200×200**。
4. **Given** 同上，**When** 检查页面级横向溢出，**Then** 恒为 **0**
   （修复后内容真实占宽，不得引入「页面左右晃动」这条新问题）。
5. **Given** 在上述任一断言失败时，**When** 读失败信息，**Then** 能区分是**内容区**、**内容容器**
   还是**菜单容器**出的问题——不得是「某个元素宽度不对」这种无法定位的表述。

### User Story 3 - 护栏对自己的假绿免疫 (Priority: P3)

维护者能确信这套用例**真的在断言**，而不是「跑绿了但其实什么都没测」——
这是本仓已经栽过两次的坑。

**Why this priority**: 它不是用户的直接诉求，但**没有它，前两条随时可能退化成第 1、2 条先例**。
排 P3 是因为前两条不依赖它，而它是前两条的**可信度前提**。

**Independent Test**: 读用例源码与它的运行输出，能指出①每一类不变式上「至少几个页面真的被断言过」，
②定向破坏时红的是**哪一条**。

**Acceptance Scenarios**:

1. **Given** 用例跑完，**When** 读输出，**Then** 报告了**每类不变式各自覆盖了几个页面/几个量**
   （例如：短页 2 个、长页 1 个、窄屏 4 个），且这些计数有**下限断言**——
   计数掉到下限以下时用例**失败**，而不是静默跳过。**「一个都没测到」必须是红的。**
2. **Given** 数据变化导致原本的短页全部变成长页，**When** 跑用例，**Then** 它**明确失败**
   并指出「短页样本数为 0」——**宁可因数据而红，不可因数据而静默放过**。
   （这是本仓的既定取向：091 的教训是「跳过」比「假红」昂贵得多。）
3. **Given** 定向破坏（把 090 或 091 的修复改回缺陷写法），**When** 跑用例，
   **Then** 失败的是**对应的那一条**不变式，且留痕（破坏前/破坏后/还原后三次运行输出）。

### Edge Cases

- **滚动条占位**：无头 Chromium 用覆盖式滚动条，`clientWidth` 等于视口宽；
  但某些平台用经典滚动条、`clientWidth` 会比视口宽小约 15px。
  ⇒ 判据必须给一个**写明数值的**容差（见「口径边界」），不得要求严格相等，
  也不得把容差放大到足以掩盖缺陷（缺陷态是 24，与 351 差一个数量级）。
- **视口必须由用例显式设定**：不得依赖 Playwright 的默认视口
  （默认值会随版本变，今天 `Desktop Chrome` 是 1280×720）。1280×720 与 375×812 都要在用例里写明。
- **窄屏判定不得走 `matchMedia`**：单测环境把它桩成恒 `false`；为避免两套口径混用，
  窄屏一律用**显式视口**，不用媒体查询判定。
- **数据量变化**：同一路径的行数会变（`/quotas` 今天是 1 行、`/orders` 2 行），
  短/长页的归属**必须运行时判定**，不得写死「`/quotas` 是短页」。
- **后端不归本项管**：e2e 打的是**已经在跑的后端**，不一定是本次改动。
  几何判据是**纯前端**的，但页面要能渲染出卡片与表格，故仍需登录成功；
  验收口径里必须写明这条前提（见 Assumptions）。
- **页脚高度可能变**：`/quotas` 的余量 56.4 = 页脚 36.4 + 内容区下内边距 20 + 卡片下外边距 0。
  ⇒ 判据一律**相对**，页脚高度**在用例里现量**，不写死 36 或 56。
- **`/departments` 没有分页**（Card + Tree，0 行）：不得对「每一页都有分页」做断言。

## Requirements *(mandatory)*

### Functional Requirements

**护栏的存在与覆盖**

- **FR-EG-001**: 端到端用例集 MUST 包含一组**几何不变式断言**，覆盖：
  ① 列表页内容区撑满（090 的核心判据）；② 窄屏外壳宽度链条与菜单条几何（091 的核心判据）。
- **FR-EG-002**: 该用例集 MUST 由既有的 `pnpm run test:e2e` 命令**收走并执行**
  （即落在 Playwright 的测试目录与命名约定之内），MUST NOT 需要额外的命令或人工步骤才会跑。
- **FR-EG-003**: 用例 MUST **显式设定**它依赖的视口（1280×720 与 375×812 各一处），
  MUST NOT 依赖测试框架的默认视口。
- **FR-EG-004**: 用例 MUST 复用既有的登录前置（`e2e/helpers/login.ts`），
  MUST NOT 自己重写一份登录流程。

**不变式的**量取口径

- **FR-EG-005**: 「卡片是否吃满内容区」的判据 MUST 表述为**相对量**：
  `滚动盒底边 − 滚动盒自身下内边距 − 卡片底边 − 卡片自身下外边距 == 0`。
  MUST NOT 写死 `664` / `624` / `56` 这类绝对像素——
  它们只能作为**本次实测的对照读数**出现在规格与注释里。
- **FR-EG-006**: 「余量是否只剩可解释的外壳占位」的判据 MUST 表述为：
  `视口底边 − 卡片底边 == 页脚实测高 + 内容区下内边距 + 卡片自身下外边距`，
  其中**页脚高度在用例里现量**，不得写死。
- **FR-EG-007**: 窄屏的**内容区可见宽度**与**内容容器宽度** MUST 作为**两个独立的断言**：
  前者对齐**视口宽度**，后者对齐**前者减 24**。
  MUST NOT 只断言两者之差（那会同时被缺陷态 24 / 0 满足）。
- **FR-EG-008**: 窄屏**菜单容器**的判据 MUST 为：宽 = 内容区可见宽度；高 = 其声明高度（48）。
- **FR-EG-009**: 页面级横向溢出（文档根的可滚动宽度超出视口宽的那部分）MUST 恒为 **0**，
  在窄屏与宽屏两侧都断言。

**反假绿（本项的核心质量要求，非可选）**

- **FR-EG-010**: 每一类不变式 MUST 附带**活性断言**：用例 MUST 报告该类里**实际被断言的样本数**，
  并对该计数设**下限**；计数低于下限时 MUST **失败**（而不是跳过）。
  「零样本」MUST 是**红色**。
- **FR-EG-011**: 短页 / 长页的归属 MUST **运行时判定**（依据「滚动盒是否溢出」），
  MUST NOT 写死路径清单。当短页样本数为 0 时，用例 MUST **明确失败**并说明原因。
- **FR-EG-012**: 对**长页**MUST 断言其「按内容撑高」的契约（滚动盒确实溢出、
  末行完整可见、卡片底边不低于那条外壳占位线），MUST NOT 对长页断言「填满」。
- **FR-EG-013**: 断言失败时 MUST 能定位到**具体页面 + 具体量**（哪一页、内容区/内容容器/菜单/卡片），
  MUST NOT 只报一个笼统的元素宽度不符。
- **FR-EG-014**: MUST 留下**定向破坏留痕**：把 090 的修复与 091 的修复分别改回缺陷写法，
  各自确认用例**变红且红在对应的不变式上**；还原后复跑**转绿**。留痕为三次运行的输出。

### 非目标（本项明确不做）

1. **不做宽屏五档的外壳零变化**（091 的 SC-004）：它需要**冻结一份基线快照**，
   基线会随任何外壳样式调整而红——比它要防的风险更脆，且 091 已用**字节级 diff** 人工做过一次。
   已在范围决策中明确划出。
2. **不做各页面在窄屏下的观感适配**：表格横向滚动、表单从两列改一列、弹窗宽度、统计卡折行——
   091 已把它们明确列为「预期仍然存在、且不算失败」。本项只守**外壳**几何。
3. **不改任何生产代码**：本项是**纯新增测试**。若在写用例的过程中发现**真缺陷**，
   另立一项处置，MUST NOT 在本项里顺手修（否则「护栏变绿」与「缺陷被修」两件事纠缠不清）。
4. **不引入新的测试框架或依赖**：用既有的 Playwright。
5. **不改动画/视觉细节**（颜色、圆角、字号、过渡），只守**几何**。
6. **不守非列表页的几何**（表单页、详情页、仪表盘、数据大屏）：090 已核实它们不受列表页撑满规则影响，
   091 已核实数据大屏不渲染常规外壳。

### Key Entities

不涉及数据实体。本项的「实体」是**四个几何量**与它们之间的**算术关系**——
名字必须钉死，因为 091 刚因为两个量共用一个名字而订正过一次
（见 `specs/091-narrow-shell-collapse/spec.md` 的「订正块」）：

- **内容区**（滚动盒子）：承载页面内容的可滚动区域。
  **内容区可见宽度** ≡ 其 `clientWidth`，**含其自身左右各 12px 的内边距** ⇒ 窄屏下等于**视口宽度**。
- **内容容器**：内容区内部的内容盒。**内容容器宽度** ⇒ 窄屏下等于**视口宽 − 24**。
  它是**另一个量**，不是「内容区可见宽度」。
- **页面根卡片**：列表页承载表格/树的那张卡片（ProTable 页是表格卡，需排除搜索表单卡）。
  **卡片底边**与**卡片自身下外边距**是「是否吃满」的两个输入。
- **菜单容器**：窄屏下的顶部菜单条 / 宽屏下的侧边栏。窄屏下**宽 = 内容区可见宽度**、**高 = 48**。
- **外壳占位**：卡片下方必须存在的可见外壳高度总和 = 页脚高 + 内容区下内边距 + 卡片下外边距。
  它是「余量是否只剩可解释部分」的比较基准，**必须现量**。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-EG-001**: `pnpm run test:e2e` **一条命令**即可跑到本项的全部几何断言；
  新增用例数 ≥ 3 个测试文件级/describe 级单元（列表页短页、列表页长页、窄屏外壳），
  且**既有 5 个 e2e 文件不减少、不新增失败**。
- **SC-EG-002**: 短页列表页的「吃满」不变式在**至少 2 个**采样页上成立
  （今天实测：`/quotas` 1 行、`/orders` 2 行、`/data-retention`、`/departments` 四页均为短页），
  且该计数**有下限断言**。
- **SC-EG-003**: 窄屏外壳的三个量在 **375×812** 下的实测对照读数为
  **内容区可见宽 375 / 内容容器宽 351 / 菜单 375×48**（四张采样页逐页一致），
  且页面级横向溢出恒 **0**。判据以**相对量**表述（见 FR-EG-007/008），上述读数作为对照基准。
- **SC-EG-004**: 长页（`/customers`，今天 19 行）的「按内容撑高」契约成立：
  滚动盒确实溢出、末行完整可见、卡片底边不低于外壳占位线；**不得**对它断言「填满」。
- **SC-EG-005**: **活性**：用例输出中能读到**每类不变式各自的样本数**，
  且这些计数**有下限断言**——把任一类的样本数人为置 0（例如把该类的采样页全部划走）
  会**导致失败**，而不是静默通过。
- **SC-EG-006**: **可证伪**：留痕证明护栏**会红**——
  ① 破坏 090 的修复（去掉「列表页撑满」的一个入口）→ 短页不变式失败；

## Assumptions

- **被测系统已就绪**：dev server 在 `http://localhost:5173`（Playwright 可自起，
  配置为 `reuseExistingServer: true`）、后端在 8081 且验证码关闭（`crm.captcha.enabled=false`，默认即是）。
  登录凭据为 `admin` / `admin123`，验证码填占位值 `0000`。
- **e2e 打的是「已在跑的后端」，不一定是本次改动**：几何判据是纯前端的，
  但写证据前**仍须**比对后端进程启动时间与 `.class` 的 mtime——这是本仓的既有规矩
  （把「别人的后端」当成自己的验证，曾是一次真实教训）。
- **数据是活的**：采样页的行数会随使用变化，短/长页归属因此**运行时判定**。
  当数据增长使短页样本归零时，用例**因数据而红**是**预期行为**（见 FR-EG-011），
  处置方式是**增补采样页**，不是放宽判据。
- **视口宽度的口径**：按 CSS 像素计；浏览器缩放 / 系统 DPI 缩放不在本项范围内。
- **像素取整**：几何量用 `getBoundingClientRect()` 的浮点值，
  断言时按**整数像素容差**（±1px）比较；本项全部不变式在实测中都是整数值或 .4/.6 这类半像素偏移。
- **口径边界——滚动条占位**：无头 Chromium 用覆盖式滚动条（`clientWidth` == 视口宽）；
  经典滚动条平台会少约 15px。故「内容区可见宽 = 视口宽」这条**允许 ≤16px 的容差**，
  且容差数值**写死在用例里并注明理由**；缺陷态是 24，与此容差相差一个数量级，不会被放过。
- **本项不新增任何运行时依赖**，Playwright 已在 `frontend/node_modules` 中（`^1.x`，随项目既有版本）。
