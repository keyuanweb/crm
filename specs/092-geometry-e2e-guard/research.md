# 研究：列表页与窄屏外壳几何的端到端护栏（092）

**日期**：2026-09-14 ｜ **输入**：[spec.md](./spec.md) ｜ **形制**：纯新增测试，零后端改动、无迁移、无契约变更、无数据实体

本轮全部结论均为**实测**（Playwright 打真实 dev server，本机，2026-09-14）。
凡未直接量的，一律标 `【推导】` 并列入 §8 的未验证项。

---

## §1 判据的表述：相对量，不写死绝对像素

**Decision**：所有几何判据表述为**几何量之间的算术关系**；绝对像素只作**对照读数**出现在规格与注释里。

| 判据 | 表述（断言的就是这个式子） |
|---|---|
| 短页「吃满」 | `滚动盒底边 − 滚动盒自身下内边距 − 卡片底边 − 卡片自身下外边距 == 0`（±1px） |
| 短页「余量只剩外壳占位」 | `视口底边 − 卡片底边 == 页脚实测高 + 内容区下内边距 + 卡片下外边距`（±1px） |
| 长页「按内容撑高」 | `滚动盒 scrollHeight > clientHeight` 且 `fill ≤ 0`（不得缩回去） |
| 窄屏宽度链条 | `内容区可见宽 ≈ 视口宽`（容差见 §3）；`内容容器宽 == 内容区可见宽 − 24` |
| 窄屏菜单 | `菜单容器宽 == 内容区可见宽`；`菜单容器高 == 48`（其声明高度） |
| 横向溢出 | `documentElement.scrollWidth − innerWidth == 0` |

**Rationale**：090 的绝对读数（`gap=56.4`、`cardBot=664`、`pagerTop=624`）依赖三个会独立变化的东西——
视口高、页脚高、内容区内边距。任一变一次，写死的门禁就**假红**，而假红会让人去改门禁而不是查问题。

**Alternatives considered**：
- *冻结一份基线快照 JSON，跑完逐项比对*：**否决**。这正是 091 的 SC-004 做过一次的做法（人工 byte-diff），
  也是本次范围决策里被划出去的那一档——快照会随**任何**外壳样式调整而红，包括无害的调整。
- *只断言「不溢出时卡片底边 == 内容盒底边」*：**部分采纳**（这就是 `fill == 0`），
  但**单靠它不够**——见 §4 的活性问题。

## §2 等待策略：两阶段，且必须自证收敛

**Decision**：两阶段等待，**不用固定 sleep**。

```
阶段一「要素齐备」：等 .page-scroll + .ant-layout-footer + .ant-layout-content + 页面根卡片
                    四者都在场，且 .ant-spin-spinning 不存在
阶段二「几何自稳定」：每 100ms 重读一遍判据所需的全部输入（四舍五入到整像素），
                    连续两次读数完全相同才继续；8s 超时 ⇒ 抛错 ⇒ 用例红
```

**实测（本机，2026-09-14）**：

| 页面 | 首张卡片出现 | 卡片在场且无 spinner | 几何最后一次变化 | `waitStable` 收敛 |
|---|---|---|---|---|
| `/quotas` | 107ms | 107ms | 497ms | **511ms** |
| `/customers` | 67ms | 67ms | 445ms | **520ms** |
| `/data-retention` | 67ms | 67ms | 395ms | **456ms** |

**关键发现：只等「卡片出现」是不够的**——卡片在 67–107ms 就出现了，但几何要到约 **400–500ms** 才定下来
（在其后 1.2s 复读，8 页逐页**完全相同**，见下表）。任何以「卡片在不在」为就绪信号的写法都会读到**中间态**。

**「稳定」不是侥幸，已证伪过**：收敛后再等 1.2s 重读，`/quotas` `/orders` `/data-retention` `/departments`
`/roles` `/users` `/customers` `/tags` **8 页逐页读数完全相同**。

**Rationale**：阶段二等的是**判据本身依赖的那些量**，不是某个代理信号——
所以它不可能「等错了东西」。且它**自证收敛**：超时就抛错，不存在「等到一半就继续」的静默路径。

**Alternatives considered**：
- *`waitForLoadState('networkidle')`*：否决。它等的是网络静默，**与布局无关**；
  且本仓后端是共享的，网络静默时机不受本项控制。
- *固定 `waitForTimeout(1500)`*：否决。它是**猜**，慢机器上会翻车，而且它把「没等到」变成「等够了」——
  正是本仓两次先例的形态。
- *只等卡片 + spinner 消失*：**实测不足**，见上表的「几何最后一次变化 ~400–500ms」。

## §3 滚动条占位：本机是覆盖式，容差仍保留

**Decision**：保留「`内容区可见宽 ≥ 视口宽 − 16`」这一容差，数值**写死在用例里并注明理由**。

**实测**：本机 Playwright chromium 是**覆盖式滚动条**，一处占位都没有——

| 元素 | `clientWidth` | `offsetWidth` | 差 |
|---|---|---|---|
| `documentElement`（`/stats`，无滚动条） | 1280 | 1280 | **0** |
| `documentElement`（`/customers`，有滚动条） | 1280 | 1280 | **0** |
| `.page-scroll`（`/customers`，自身有滚动条） | 1080 | 1080 | **0** |

**Rationale**：本机实测差为 0，但容差**仍要留**——CI 的 ubuntu runner 与本地 Windows 的滚动条实现
**不保证一致**，而「跑绿一次、换台机器假红」正是本项要消灭的形态。16px 这个数取自经典滚动条的典型占位（约 15px）向上取整。

**容差不会掩盖缺陷**：缺陷态的内容区可见宽是 **24**，与 375 差 **351**——容差 16px 与它相差一个数量级以上。
`/customers` 这一页顺带证明：即使 `.page-scroll` 自己有竖直滚动条（`scrollHeight > clientHeight`），
`clientWidth` 也不受影响。

**顺带确认的一处口径**：宽屏下 `.page-scroll` 宽 **1080**（= 1280 − 侧边栏 200），
**不是**视口宽——所以「内容区可见宽 = 视口宽」这条判据**只在窄屏成立**（窄屏不渲染侧边栏）。
spec 已把它限定在窄屏，此处从数据上确认了这个限定的必要性。

## §4 短/长页判定与样本：运行时判定 + 活性下限

**Decision**：短/长页**运行时判定**（依据滚动盒是否溢出），采样页只作**候选清单**；
每类不变式报告**实际被断言的样本数**并设**下限**；下限不满足 ⇒ **用例红**。

**实测（1280×720，2026-09-14）**：

| 页面 | 行数 | 溢出 | `fill` | 判定 |
|---|---|---|---|---|
| `/quotas` | 1 | 0 | 0 | 短页 |
| `/orders` | 2 | 0 | 0 | 短页 |
| `/products` | 5 | 0 | 0 | 短页 |
| `/tags` | 1 | 0 | 0 | 短页 |
| `/invoices` | 1 | 0 | 0 | 短页 |
| `/data-retention` | 1 | 0 | 0（`cardMb=16`） | 短页（Card 根） |
| `/exports/scheduled` | 0 | 0 | 0（`cardMb=16`） | 短页（Card 根） |
| `/departments` | 0 | 0 | 0（`cardMb=16`） | 短页（Card 根） |
| `/roles` | 14 | **65** | −65.75 | 长页（**脆**） |
| `/users` | 20 | **365** | −365.75 | 长页 |
| `/customers` | 20 | **415** | −415.75 | 长页 |
| `/leads` | 11 | **358** | −358.125 | 长页 |
| `/recycle` | — | — | — | **404 页，排除**（见下） |

**选定的样本与理由**：

- **宽屏短页候选**（4 页）：`/quotas`、`/orders`（**ProTable 根**，走 090 的入口 A）、
  `/data-retention`、`/departments`（**Card 根**，走入口 B）。
  ⇒ 两个入口**各有样本**，缺哪个入口都会红。下限：**短页 ≥ 2，且至少 1 个 ProTable 根、至少 1 个 Card 根**。
- **宽屏长页候选**（2 页）：`/users`（溢出 365）、`/customers`（溢出 415）。下限：**≥ 1**。
  **`/roles` 明确排除**：它只溢出 **65px**，数据再少几行就会变短页——作「长页」样本太脆。
  `/leads` 备用。
- **窄屏候选**（4 页）：`/stats`、`/customers`、`/orders`、`/roles`。
  与 091 取证用的是**同一组**，保持可比。下限：**≥ 4**（窄屏判据与数据无关，没有跳过风险）。
  实测四页逐页一致：内容区 **375** / 容器 **351** / 菜单 **375×48** / `docOverflow` **0**。

**`/recycle` 为什么排除**：实测它渲染的是 `.ant-result.ant-result-404`（**路由不存在**），
根本没有页面根卡片（`cardBottom=null`）。把它留在候选里会让「根卡片选择器」在无声中被判为失效——
**这是一次真实的候选清单核对，不是形式检查**。

**Rationale（活性下限为什么是硬要求）**：短/长页归属依赖**活数据**——
`/customers` 这一页在两次探针之间就从 19 行变成了 20 行。若判据写成
「**若**没溢出**则**断言填满」，数据一变就可能**永远不满足条件、断言从不执行**，而套件全绿。
这不是假设：本仓的 091 缺陷就在**全站内容宽 0** 的同时**全量测试全绿**（断言全落在文案上）；
048 的 e2e 套件更是 22/23 用例**从未被执行过**却长期存在。

**Alternatives considered**：
- *写死路径清单（「`/quotas` 是短页」）*：否决。数据一涨，断言还在跑但语义已经不成立。
- *溢出时 `test.skip()`*：否决。**skip 就是本项要消灭的那个东西**——
  它把「没测到」伪装成「测试通过」。本项采用「红」：数据让短页样本归零时，用例明确报
  「短页样本数为 0」并失败，处置是**增补采样页**，不是放宽判据。

## §5 窄屏「菜单容器」的锚点

**Decision**：锚点为 **`.ant-menu` 的直接父元素**；并断言 `menuBox.parentElement` 就是
外壳布局节点（即它是外壳的直接子元素，不是某个嵌套菜单）。

**实测**：四页逐页 `outer.firstElementChild === document.querySelector('.ant-menu').parentElement` **为真**
（即两种取法**同一节点**），四页都是 `DIV`（091 修复后用的普通容器，无类名）、**375×48**。

**Rationale**：`outer.firstElementChild` 依赖「外壳的第一个子元素就是菜单条」这一位置假设；
锚在 `.ant-menu` 上则是**语义**的（「承载菜单的那个容器」），与 spec 的 Key Entities 定义一致。
再加一条 `parentElement === 外壳布局节点` 的断言，是为了让「菜单容器」这个识别**不可能认错对象**——
认错时失败信息会直接说清，而不是给出一个莫名其妙的小数值。

**顺带证实 091 的订正**：`菜单.scrollWidth − clientWidth == 0`（四页全部），
即窄屏菜单**没有可滚动余量**——形态是 `...` 溢出折叠，**不是**横向滚动。
本项**不得**重新引入「横向滚动」的说法。

## §6 文件布局与命令接入

**Decision**：新增 3 个文件，**不改 `playwright.config.ts`**。

```text
frontend/e2e/
├── helpers/
│   ├── login.ts                    # 既有，复用，不改
│   └── geometry.ts                 # 新增：量取表达式、两阶段等待、常量、分类与活性报告
├── geometry-list-page.spec.ts      # 新增：090 的不变式（宽屏 1280×720）
└── geometry-narrow-shell.spec.ts   # 新增：091 的窄屏不变式（375×812）
```

**接入方式**：Playwright 的默认 `testMatch` 是 `**/*.@(spec|test).?(c|m)[jt]s?(x)`，
`testDir` 已是 `./e2e` ⇒ **新 `*.spec.ts` 自动被 `pnpm run test:e2e` 收走**，
`helpers/geometry.ts` 不被收走（与既有 `helpers/login.ts` 同理）。CI 的 `e2e` 作业已在跑该命令，**无需改动**。

**`playwright.config.ts` 不改**：`retries: 0` 保持——本项不靠重试掩盖 flake，靠 §2 的确定性等待；
`timeout: 30s` 保持——被测的最长用例是宽屏 6 次页面加载，实测每次 `waitStable` ≈ 0.5s。
**无 viewport 覆盖**也保持不改：spec 要求视口**由用例显式设定**（`test.use({ viewport })`），
正好利用「配置层不设、用例层显式设」这一分工。

**Alternatives considered**：
- *放进一个 `geometry.spec.ts`*：否决。两件事的**视口不同、失败语义不同**，
  混在一起会让「窄屏坏了」和「列表页坏了」在报告里难以区分（FR-EG-013 要求可定位）。
- *在 `playwright.config.ts` 里加 project 分别设视口*：否决。会改动**全部**既有用例的运行环境
  （5 个既有 e2e 文件的视口会随之变化），影响面远超本项。

## §7 可证伪：三条定向破坏（对应 SC-EG-006）

破坏点已逐一定位并核实存在：

| # | 破坏 | 位置 | 预期变红的判据 |
|---|---|---|---|
| ① | 注释掉「列表页撑满」**入口 A**（ProTable 根） | `frontend/src/index.css:400`（`.page-fade > .ant-pro-table,` 起的那条规则块） | 短页 `fill == 0` 在 **ProTable 桶**上失败；Card 桶应**仍绿** |
| ② | 注释掉同段**入口 B**（Card 根） | `frontend/src/index.css:415`（`.page-fade > .ant-card:has(...)`） | 短页 `fill == 0` 在 **Card 桶**上失败 |
| ③ | 窄屏照样渲染侧边栏 | `frontend/src/App.tsx:703`（`{isMobile ? (` → `{false ? (`） | 窄屏「内容区可见宽 = 视口宽」失败（实测会退回 **24**） |

**①与②分开做**的价值：它们证明**报告是可定位的**——失败信息要指出是哪几页、
而不是笼统的「几何不对」。这也是对 FR-EG-013 的验证。

**③ 是 091 自己用过的那一次破坏**（其 `falsification-evidence.md` 留痕），本项复用它以保证可比。

**纪律**：三次破坏**都是临时的、逐个还原**；每次还原后必须 `git status` 确认工作区干净、
`git diff` 确认生产代码**逐字节回到原样**。破坏期间**不得**提交任何东西。

## §8 已知风险与未验证项（如实列出）

1. **CI 与本地滚动条实现可能不同**：本机实测差为 0，CI 未验（本仓无远端、CI **永不触发**，
   见 083/T069 的既定口径）。§3 的 16px 容差是为它准备的，但**未在 CI 上实测过**。
2. **`/customers` 的行数会变**（本轮探针两次读到 19 与 20 行）：长页桶靠它时，
   数据缩到不溢出就会翻转归类。故长页下限取 **≥1** 且备有 `/users`、`/leads`，
   真发生翻转时用例**会红并说明「长页样本数为 0」**——**这是预期行为，不是缺陷**。
3. **`fill` 的 ±1px 容差是选定的、不是量出来的**：实测 8 页短页 `fill` 全部**恰为 0.00**，
   但半像素布局（实测有 `.4` / `.6` 的底边）在别的缩放下可能产生 1px 级偏差。
   `【推导】`1px 足够；若实现时发现需要更大容差，**必须写明理由**，不得默默放大。
4. **窄屏判定不走 `matchMedia`**：本项全部窄屏判据靠**显式视口**。
   `src/test/setup.ts` 把 `matchMedia` 桩成恒 `false` 是**单测**的事，e2e 里媒体查询是真的——
   但两套口径混用是 091 踩过的坑，故本项**一律不用**。
5. **未验证：把本项用例放进 CI 的 `e2e` 作业后能否跑通**（CI 从不触发，无法实测）。
   本地等效命令即 `pnpm run test:e2e`，与 CI 作业执行的是同一条。
6. **未验证：并发跑 e2e 与人工操作同一 dev server 时的相互影响**。
   本项用例**只读**（不点提交、不改数据），但登录会写会话；风险低，未实测。
7. **本项不覆盖的几何**（spec 非目标）：宽屏五档外壳零变化、各页面的窄屏观感适配、
   非列表页几何、动画与视觉细节。
8. **若写用例时发现真缺陷**：spec 非目标第 3 条已定——**另立一项**，
   不得在本项里顺手修（否则「护栏变绿」与「缺陷被修」纠缠，定向破坏的留痕失去意义）。
